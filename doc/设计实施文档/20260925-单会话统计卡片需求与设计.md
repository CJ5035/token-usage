# 单会话统计卡片 — 需求与设计

- 日期：2026-09-25
- 范围：使用记录页「会话用量」表行下钻 + 单会话统计卡片；归一投影补 `ttft_ms`；`/api/usage/records` 加 `group_id` 过滤
- 不在范围：会话聚合查询性能、WorkBuddy/DSH 接入记录页、会话表列结构调整

---

## 1. 需求

用户希望能看到**单个会话维度**的 Token 用量统计，包含：会话轮数、模型输出速度（tok/s）、首 token 延迟、累计输入/输出 Token、缓存命中率。

### 1.1 现状盘点（已核实）

记录页（`app/web/index.html:204-231`）是两张表叠放：上「会话用量」(`loadSessions` @ `app.js:2032`)、下「使用记录」(`loadRecords` @ `app.js:2092`)。

**已有**：`unified_sessions_page`（`db.py:4343-4425`）每行已返回 `request_count`、`total_input_tokens`、`total_output_tokens`、`avg_tps`、`speed_samples`、`cache_hit_tokens`、`uncached_input_tokens`、`cache_write_tokens`。也就是说**命中率的三个输入项后端已经算好了，只是没算成率、前端也没展示**。

**缺三件**：

1. **无法下钻单个会话**。`/api/usage/records` 只接受 `page / page_size / model / days / source`（`server.py:2115-2145`），没有会话维度的过滤参数；会话行也不可点击。
2. **首 token 延迟没进归一投影**。`zcode_usage.ttft_ms` 实测 18960/24221 行有值，但 `_unified_source_sql`（`db.py:4190-4260`）的四段投影里没有这一列，记录页与会话聚合都拿不到。它目前只用在统计页 ZCode 区块的「平均首字延迟」KPI（`app.js:1124`）。
3. **命中率没算**。`unified_sessions_page` 返回了 `cache_hit_tokens` / `uncached_input_tokens` / `cache_write_tokens`，但没有 `hit_rate` 字段。

### 1.2 关于「输出速度」口径

需求里提的口径是「输出 token ÷（请求耗时 − 首 token 延迟）」。**这正是项目已实现的口径**，无需新建计算：

- `_ZCODE_GEN_SQL`（`db.py:1774-1782`）算有效生成窗口 = `duration_ms - ttft_ms`，并对 TTFT 占比 ≥90% 的失真行改用 TTFT 本身作窗口，TTFT 缺失/越界则整个 duration 计入。
- `_ZCODE_TPS_SQL`（`db.py:1785-1789`）= `output_tokens * 1000.0 / 有效窗口`，且只保留可信样本（输出 ≥10 token、窗口 ≥100 ms、速率 ≤500 tok/s），其余置 NULL 不参与 AVG。

`claudecode_usage.speed_tps` 与 `codex_usage.speed_tps` 是各自采集层写入的原列。会话卡片直接用 `unified_sessions_page` 已有的 `AVG(speed_tps)`，口径与统计页一致。

## 2. 设计

### 2.1 归一投影补 `ttft_ms`

`_UNIFIED_COLS` 末尾追加 `ttft_ms`，四段各补一列：

| 段 | `ttft_ms` 取值 |
|---|---|
| `usage_records` | `NULL`（表无此列） |
| `zcode_usage` | `z.row_ttft` —— 内层子查询在已有 `row_tps` 旁再算一个 `({_ZCODE_TTFT_SQL}) AS row_ttft` |
| `claudecode_usage` | `NULL`（表无此列） |
| `codex_usage` | `NULL`（表无此列） |

沿用 `_ZCODE_TTFT_SQL`（`db.py:1791-1793`）的有效性判定：`ttft_ms` 需落在 `[0, duration_ms]` 内，否则 NULL 不参与统计。

> **口径必须说清**：首 token 延迟**只有 ZCode 有数据**。其余三个来源恒为 `—`，卡片上必须标注原因，不能让用户以为是 0 或故障。

### 2.2 会话分组键抽成常量（DRY，本设计的关键前提）

`unified_sessions_page` 目前在函数体内内联拼 `session_key` 与 `group_id`。记录明细要按同一个键过滤，两处表达式**必须逐字相同**，否则下钻会漏行或串行。故抽成模块级常量：

```python
_UNIFIED_SESSION_KEY_SQL = (
    "CASE WHEN session_id IS NOT NULL AND session_id != '' THEN session_id "
    "WHEN key_id IS NOT NULL AND key_id != '' THEN key_id ELSE source_record_id END"
)
_UNIFIED_GROUP_ID_SQL = (
    "source || ':' || COALESCE(account_id, '') || ':' || " + _UNIFIED_SESSION_KEY_SQL
)
```

两个函数都引用常量，不再各自拼字符串。

### 2.3 会话聚合补三个字段

`unified_sessions_page` 的聚合 SQL 追加：

```sql
AVG(ttft_ms) AS avg_ttft_ms,
COUNT(ttft_ms) AS ttft_samples
```

Python 侧新增三个返回字段：

- `avg_ttft_ms`：`round(float(...), 1)`，无有效样本为 `None`
- `ttft_samples`：有效 TTFT 行数（前端据此区分"无数据"与"0 ms"）
- `hit_rate`：`hit / (hit + miss + cw) * 100`，`round(..., 2)`，分母为 0 时 `0.0`

**`hit_rate` 必须用项目现行口径** `cache_read / (cache_read + uncached_input + cache_write)`，即 `命中 / 总输入`。这是 `doc/20260907-hit-rate-formula-fix.md` 统一过的公式，`db.py` 里 15 处聚合函数全部用它。**不得**写成 `hit/(hit+uncached_input)` —— 那是被该文档明确否决的旧口径，会让命中率系统性虚高。

### 2.4 `/api/usage/records` 加 `group_id` 过滤

- `unified_records_page(source, page, page_size, model, days, group_id=None)`：`group_id` 非空时在归一投影外层加 `WHERE {_UNIFIED_GROUP_ID_SQL} = ?`。
- 路由 `/api/usage/records?group_id=<id>`。**`group_id` 要求同时带 `source`**：缺省 `source` 会走 `db.usage_records_page` 这条不认识会话分组的 legacy 路径，此时给出 400 而非静默忽略。
- `filter` 回显里带上 `group_id`，便于前端与调试核对。

**等价性已验证**：`artifacts/probe_session_card.py` 在真实库上取请求数最多的 8 个会话，逐个比对"按 `group_id` 过滤明细后再聚合"与"会话表那一行的聚合"，`request_count` / `total_tokens` / `total_input_tokens` / `total_output_tokens` / `cache_hit_tokens` / `cache_write_tokens` / `ttft_samples` **七项全部一致**。

### 2.5 前端：行下钻 + 统计卡片

- 会话表每行挂 `data-gid`，整行可点击；点击后：
  1. `state.records.groupId = gid`、`state.records.session = <该行对象快照>`
  2. 该行加选中态样式
  3. 下方明细表回第 1 页并带 `group_id` 重载
  4. 渲染统计卡片
- **卡片数据零额外请求**：`loadSessions` 的响应里每行已含全部 6 个指标所需字段，点击时直接用内存中的那个对象。
- 卡片用现有 `.tc-grid.tc-6` 六格栅格（`style.css:329-334`，与统计页「Token 构成」同一套 `.tc/.tc-l/.tc-v/.tc-s` 视觉）：

| 格位 | 主值 | 副文案 |
|---|---|---|
| 会话轮数 | `request_count` | `request_count_exact=false` 时前缀 `≥` 并注明"聚合日志" |
| 输出速度 | `avg_tps` `tok/s` | 有效样本 `speed_samples/request_count` |
| 首字延迟 | `avg_ttft_ms` `ms` | 有效样本 `ttft_samples/request_count`；`ttft_samples=0` 时主值 `—`、副文案说明"仅 ZCode 提供" |
| 累计输入 | `total_input_tokens` | 含缓存命中 |
| 累计输出 | `total_output_tokens` | — |
| 缓存命中率 | `hit_rate` `%` | 命中量 `cache_hit_tokens` |

- 卡片右上角「清除」按钮：清掉 `groupId` 与 `session`、去掉选中态、明细表回第 1 页不带过滤、隐藏卡片。
- 切来源 / 切模型 / 后台导入触发的回第 1 页，都要顺带清除会话选择（否则会出现"卡片显示 A 会话、明细表却是全量"的错位）。

### 2.6 实时更新

需求提到"随会话进行实时更新"。本程序是**只读本机数据的旁路面板**，不参与会话过程，没有推流通道。既有机制已能覆盖：本机渠道启动时增量导入 + 设置页的自动同步间隔；导入完成后 `refreshCodexVisible`（`app.js:1787-1793`）会把记录页两表拉回第 1 页重载。卡片跟随 `loadSessions` 的响应刷新即可，**不新增轮询**（YAGNI）。

## 3. 与「记录页查询性能优化」计划的关系（重要）

`docs/superpowers/plans/2026-09-25-records-page-query-perf.md` 同样改动 `_unified_source_sql` 与 `unified_records_page`，两份计划有冲突面。

### 3.1 当前真实状态（2026-09-25 复核）

性能计划的 **Task 1-2 已执行并提交**：

```
4d6f910 perf(db): prune unified union arms by source and push filters into base tables
77a3b99 test: characterize unified query outputs and time-column invariant
```

所以 `app/db.py`（现 4541 行）已是**分段注册表形态**：有 `_UnifiedArm` / `_UNIFIED_ARMS` / 四个 `_unified_arm_*` 投影函数 / `_unified_arm_inner`；`_unified_filter` 已删除；`_unified_source_sql(source, model, days)` 返回 `(sql, params)`。

性能计划的 **Task 3-7 尚未执行**：`row_limit` / `_unified_count` / `_unified_days_bound` 都还不存在。

**本计划的全部锚点已按这个真实状态重写。**

### 3.2 🚨 `group_id` 与 `row_limit` 必须互斥（正确性，非优化）

性能计划 Task 3 会给 `_unified_source_sql` 加 `row_limit`：各段基表先 `ORDER BY 时间 DESC LIMIT (offset+size)` 再 UNION。本计划的 `group_id` 过滤加在归一投影**外层**。两者同时生效时，各段取的是"**全表**最新 N 行"，再按会话筛 → 可能一行不剩，**会话有 1000 条也返回空页**。

最终代码里必须有：`group_id` 非空 ⇒ `row_limit=None`。

已在两侧都钉住：
- 本计划 Task 3 Step 3 的代码注释写明了这条约束。
- 性能计划 Task 3 Step 5 的代码已带上 `row_limit=None if group_id else page * page_size` 判断，并说明了它对本计划未落地时也安全（`group_id` 参数不存在时该分支恒取 `page * page_size`）。

### 3.3 若性能计划被回滚

则 `app/db.py` 退回四段内联 `seg_*` + `_unified_filter` 形态，本计划 Task 1/2/3 的锚点全部失效，需要反向适配：`ttft_ms` 列加回 `_unified_source_sql` 内的四个 `seg_*` 字符串；`group_id` 过滤拼在 `_unified_filter` 返回的 `where` 上。Task 4/5/6（路由与前端）不受影响。

## 4. 已评估并否决的方案

| 方案 | 否决理由 |
|---|---|
| 卡片单独开一个 `/api/usage/session-stats?group_id=` 接口 | `loadSessions` 响应已含全部字段，点击时直接用内存对象即可，加接口是白增一次往返与一份重复聚合逻辑。YAGNI。 |
| 会话表直接加「首字延迟」「命中率」两列 | 表已 12 列，窄窗口只能横向滚；卡片本就是为这几个指标设计的展示位。 |
| 用 `session_id` 而非 `group_id` 做过滤键 | `session_id` 跨来源可能重复，且空会话行按 `key_id`/`source_record_id` 兜底分组；只有 `group_id` 与会话表的分组一一对应。 |
| 给会话卡片加 WebSocket / 轮询实现"实时" | 本程序不参与会话过程，只读本机日志；既有增量导入 + 自动同步已覆盖，见 §2.6。 |
| 顺手修会话表第 9/10 列重复渲染 total 的显示 bug（`app.js:2058`） | 与本需求无关，属独立缺陷，另案。 |
| 为 `claudecode`/`codex` 估算 TTFT | 源日志无该字段，估算即编造数据。恒显 `—` 并标注原因。 |

## 5. 验收口径

1. `group_id` 过滤后的明细逐项聚合 == 会话表该行的聚合（`request_count` / 各 token 项 / `ttft_samples`）。
2. `hit_rate` 与 `db.py` 现行 15 处聚合函数同公式：`hit/(hit+miss+cw)*100`。
3. 非 ZCode 来源的会话 `avg_ttft_ms is None` 且 `ttft_samples == 0`，卡片显示 `—` 并说明原因。
4. `group_id` 不带 `source` → 400。
5. 切来源/切模型/后台导入回第 1 页时，会话选择被清除，不出现卡片与明细表错位。
6. 现有测试全绿，尤其 `tests/test_codex_server.py` 第 7 节（统一来源明细/会话路由）。

## 6. 实施结论（2026-09-26）

- 后端：`_UNIFIED_COLS` 增至 21 列（末列 `ttft_ms`）；四段投影中仅 zcode 段取
  `_ZCODE_TTFT_SQL` 现算，其余三段恒 `NULL`。
- 会话聚合新增 `avg_ttft_ms` / `ttft_samples` / `hit_rate` 三字段；`hit_rate` 走新增的
  `_hit_rate_pct()`（`db.py` 另有 14 处内联同式实现属历史遗留，本次未动）。
- 分组键收敛为 `_UNIFIED_GROUP_ID_SQL`，会话聚合与明细下钻共用。
- `/api/usage/records` 新增 `group_id`（要求同时带 `source`，否则 400）。
- 前端零新增请求：卡片 6 个指标取自 `loadSessions` 已返回的行对象。
- 测试：`tests/test_session_card.py` 共 33 个用例通过，含跨层勾稽
  （卡片指标 == 会话行 == 明细自聚合）；全量 `pytest tests -q` 948 passed。
