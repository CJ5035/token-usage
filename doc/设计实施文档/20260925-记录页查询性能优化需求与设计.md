# 使用记录页查询性能优化 — 需求与设计

- 日期：2026-09-25
- 范围：`/api/usage/records`、`/api/usage/sessions` 的 SQL 层（`app/db.py` 归一查询）与记录页前端取数节奏
- 不在范围：单会话统计卡片、TTFT 列、WorkBuddy/DSH 接入记录页（另立计划）

## 1. 问题

记录页（`app/web/index.html:204-231`）由两张表组成：「会话用量」(`loadSessions` @ `app.js:2032`) 与「使用记录」(`loadRecords` @ `app.js:2092`)。
两者分别打 `/api/usage/sessions` 与 `/api/usage/records`，后端最终都落到 `app/db.py` 的
`_unified_source_sql()` —— 一个四段 `UNION ALL` 的归一子查询（`usage_records` + `zcode_usage` +
`claudecode_usage` + `codex_usage`），过滤与排序全部加在子查询**外层**。

### 1.1 实测基线

工具：`artifacts/bench_records_page.py`（只读打开 `data/gousage.db`）。
数据量：`zcode_usage` 24221 + `claudecode_usage` 19894 + `codex_usage` 2439 + `usage_records` 660 = 47214 行。

冷缓存（进程刚启动、首次打开记录页的真实场景）：

| 查询 | 耗时 |
|---|---|
| `COUNT(*)` over union | 162.8 ms |
| 取 7 行页数据 | 64.8 ms |
| `DISTINCT model`（模型下拉） | 21.3 ms |
| sessions `COUNT(DISTINCT group)` | 50.3 ms |
| sessions 页数据 | 74.7 ms |
| 尾页 `OFFSET 47207` | 132.9 ms |

**一次开页 ≈ 375 ms 纯 SQL；每翻一页重付同样代价。**

### 1.2 根因

`EXPLAIN QUERY PLAN`（`source=zcode`，即已带来源过滤）：

```
CO-ROUTINE (subquery-5)
  COMPOUND QUERY
    LEFT-MOST SUBQUERY → SCAN r  /  SEARCH a USING INTEGER PRIMARY KEY
    UNION ALL         → SCAN z0
    UNION ALL         → SCAN c
    UNION ALL         → SCAN x
SCAN (subquery-5)
USE TEMP B-TREE FOR ORDER BY
```

1. **分支不裁剪**：`WHERE source = 'zcode'` 加在 union 外层，四张表全部全表 SCAN。谓词无法下推到各段——第一段的 `source` 是 `_report_channels_expr()` 生成的 `COALESCE(a.source,'opencode')` 表达式，SQLite 无从据此裁掉分支。
2. **排序不走索引**：`ORDER BY started_at DESC` 落在 union 结果上，只能 `USE TEMP B-TREE`，现有 `idx_zcode_time` / `idx_cc_time` / `idx_codex_usage_time` / `idx_usage_time` 全部失效。实测仅做分支裁剪、排序仍在外层时，取 7 行只从 28.29 ms 降到 25.44 ms —— **排序才是主要成本**。
3. **`days` 过滤挡住时间索引**：`datetime(started_at) >= datetime('now', ?)`（`db.py:4275`）能命中各表已有的表达式索引（`idx_zcode_utc` 等），但该索引按 `datetime(started_at)` 组织，**不能同时服务 `ORDER BY started_at DESC`**，仍需 TEMP B-TREE。实测 zcode 段 days=90 取 7 行 = 12.49 ms。
4. **模型下拉每次翻页重算**：`loadRecords` 每次都读 `data.models`，后端每次跑一遍 `DISTINCT model` 全量扫（21-24 ms），而结果只有 41 个模型、几乎不变。

## 2. 设计

### 2.1 归一分段注册表（`_UnifiedArm`）

把四段投影登记成注册表，每段携带自身基表的元信息（表名、时间列、模型列、段内 source 判定、与外层次序键等价的段内次序表达式）。在此之上：

1. **按 source 裁剪分段**：`source != 'all'` 时只拼该 source 能产出的段。
2. **过滤下推**：`source` / `model` / `days` 三个谓词写进各段的**基表子查询**，而非 union 外层。
3. **明细分页再下推 `ORDER BY` + `LIMIT`**：基表子查询追加 `ORDER BY <时间列> DESC, <段内次序键> LIMIT (offset + page_size)`，让 `idx_*_time` 同时服务过滤与排序，外层只归并极少量行。

`usage_records` 段的 source 判定依赖 `accounts.source`，段内子查询保留 `LEFT JOIN accounts`
（`COALESCE(a0.source,'opencode') = ?`）以保持与旧口径完全一致 —— 包括 `account_id`
在 `accounts` 中无对应行时回落为 `'opencode'` 的语义。该段拿不到与外层
`source_record_id`（`source || ':' || account_id || ':' || usg_id`）等价的段内表达式，
故**不下推 `LIMIT`**（只下推过滤）；`usage_records` 仅 660 行，代价可忽略。

### 2.2 `top-N` 下推的正确性

外层次序为 `started_at DESC, source ASC, source_record_id ASC`，取全局第 `[offset, offset+size)` 名。
令 `need = offset + size`。

- 若某行 x 属于全局前 `need` 名，则 x 所在段内按 `started_at DESC` 排在其前的行不超过 `need-1` 行（否则这些同段行全都全局先于 x，x 的全局排名就超过 `need`），故 x 必在该段的 top-`need` 内。
- 同段 `started_at` 并列时，段内取舍必须与外层一致，否则边界处可能漏行。因此段内 `ORDER BY` 追加**与外层 `source_record_id` 同序**的表达式：zcode 段 `('zcode:' || id) ASC`、claudecode 段 `('claudecode:' || id) ASC`、codex 段 `id ASC`。段内 `source` 恒为常量，不影响次序。

等价性由 `artifacts/probe_prototype_pushdown.py` 在真实库上对 12 组
`(source, model, days, page)` 组合验证：COUNT 与逐行数据全部一致。

### 2.3 `COUNT` 分段相加

总数改为各段基表子查询 `COUNT(*)` 相加，不再 `COUNT(*)` over union。各段走覆盖索引，实测 `source=all` 从 16.83 ms → 0.01 ms。

### 2.4 `days` 下界改为可索引的字面量比较

把 `datetime(<time_col>) >= datetime('now', ?)` 改为 `<time_col> >= ?`，参数为 Python 侧算出的 UTC ISO 下界。

**关键约束**：下界字面量必须与存储形态同形。各表时间列一律是 `YYYY-MM-DDTHH:MM:SS[.ffffff]Z`
（实测 `usage_records.created_at` 660/660、`zcode_usage.started_at` 24221/24221、
`claudecode_usage.started_at` 19894/19894、`codex_usage.started_at` 2439/2439 全部匹配）。
而 `datetime('now', ?)` 返回 `YYYY-MM-DD HH:MM:SS`（空格分隔）；空格 `0x20` < `'T'` `0x54`，
直接拿它当下界做字典序比较会**多纳入约一天的行**（实测 days=30 得 21158，正确值 19453）。
故下界用 `strftime("%Y-%m-%dT%H:%M:%S")` 形态。

等价性由 `artifacts/probe_days_rewrite.py` 与 `artifacts/probe_py_bound.py` 验证：
4 张表 × 窗口 {1,7,30,60,90,180,365} 天，`COUNT` 与取 7 行结果全部一致；计划为
`SEARCH ... USING COVERING INDEX idx_*_time (col>?)`，排序不再需要 TEMP B-TREE。
zcode 段 days=90 取 7 行：12.64 ms → 0.01 ms。

> 该改写把"时间列存 UTC `Z` 字面量"从隐含约定升级为**被依赖的不变量**，需由测试守卫。

### 2.5 模型下拉不随翻页重取

`/api/usage/records` 新增 `with_models` 参数（默认 `1`）。为 `0` 时不查 `unified_models`、响应不含 `models` 键。
前端按筛选键 `source|model` 记忆：键未变（纯翻页）时带 `with_models=0` 并保留现有下拉 DOM。

`total` 不做前端复用 —— 2.3 之后 `COUNT` 只要 0.01 ms，复用不划算且会引入与后台导入的一致性窗口。

> §1.1 的冷缓存基线（`COUNT` 162.8 ms 等）与本表的热缓存中位数不可直接相减——两者测量条件不同。本表内部前后可比，请以本表为准。

## 4. 已评估并否决的方案

| 方案 | 否决理由 |
|---|---|
| 给 `zcode_usage` 等补 `datetime(col)` 表达式索引 | 已存在：`idx_usage_utc`、`idx_zcode_utc`、`idx_cc_utc`、`idx_codex_usage_utc`、`idx_usage_acct_utc`、`idx_wbl_utc`。补了没有增量收益。 |
| 直接把 `datetime('now', ?)` 的返回值当字典序下界 | **结果错误**（见 §2.4）。 |
| 只做分支裁剪、不下推 `ORDER BY`/`LIMIT` | 取 7 行只从 28.29 → 25.44 ms，排序成本仍在。 |
| `OFFSET` 换 keyset 游标 | 下推后尾页也只 0.76 ms，收益不足以换掉 UI 的"跳页"语义。YAGNI。 |
| 物化一张 `unified_usage` 表 | 需要在四条导入路径上维护同步，复杂度与回归风险远高于收益。 |
| 前端复用 `total` | §2.5，`COUNT` 已是 0.01 ms。 |
| 补 `idx_zcode_model_time(model_id, started_at DESC)` | 确有收益（model 筛选 7.22 → 0.01 ms），但记录页前端仅在用户主动选模型时才带 `model`，且下推后已降到 13.49 ms 可接受。列为后续可选项，不在本次。 |

## 5. 验收口径

1. **行为零变化**：对 `(source, model, days, page)` 组合矩阵，`unified_records_page` / `unified_models` / `unified_sessions_page` 的返回值在改动前后逐字段一致。
2. **计划变化可观测**：`source != 'all'` 时 `EXPLAIN QUERY PLAN` 不再出现被裁剪表的 `SCAN`；带 `days` 时出现 `USING ... INDEX idx_*_time (col>?)`。
3. **不变量有守卫**：存在测试断言四张表的时间列均为 `YYYY-MM-DDT...Z` 形态。
4. **现有测试全绿**：尤其 `tests/test_codex_server.py` 第 7 节（统一来源明细/会话路由）与 `tests/test_report_api.py`。

**试做中发现并修正的 6 处问题**（已回填进计划）
1. Goal 与完成标准过度承诺"开页降到毫秒级"。用同一脚本前后各测一次的结果是：开页合计 293.22 → 224.92 ms（只降约 23%），瓶颈在范围外的会话聚合（143.26 → 131.76 ms）。已改为以"翻页 72.19 ms → 0.84 ms"为收益口径，并在计划与本文档中都写明"不得宣称开页进入毫秒级"。
2. 收益数字曾混用冷缓存（§1.1）与热缓存（§3）两套测量条件，导致 48 ms 与 250 ms 并列自相矛盾。已统一为 §3.1 的单一脚本单一口径表，并注明 §1.1 冷缓存基线不可与之相减。
3. Task 2 Step 3 插入一行 `from dataclasses import dataclass` 后，Step 4 声明的替换区间 4190-4278 实际漂移为 4191-4279；已改为按文本锚点定位并显式提示漂移。
4. `test_single_source_prunes_other_arms` 原先在 `EXPLAIN` 输出里找表名，但 `usage_records` 段的基表子查询用了别名 `r0`，计划显示 `SCAN r0` 而非 `SCAN usage_records`，断言必挂。已改为在生成的 SQL 文本上判"拼了哪些表"，计划输出只用来确认退化为单段（无 `UNION ALL` / `COMPOUND QUERY`）。
5. `test_all_source_keeps_four_arms` 同因失败；已改为在 SQL 文本上判四表齐备 + 计划里 `UNION ALL` 出现 3 次。
6. `app/db.py` 导入区行号：`import threading` 实为第 16 行（原计划写 14-18，一轮审查误改为 15-17），已更正为 16-18。

**另据两轮独立审计补入的 3 处加固**
- Task 1 Step 5 增加硬约束：生成快照前必须确认 `git status --short -- app/db.py` 无输出，否则快照会锁死新行为、安全网失效且不报错。
- `recordsFilterKey()` 处加注释说明"键不含 days"是因为记录页当前不发 days，若将来加时间范围控件必须同步并入。
- Global Constraints 补充说明 `row_limit = page * page_size` 不设上界是有意的（超过段行数时自然退化为按索引取全段，不慢于旧实现，加人为上限反而有漏行风险）。
