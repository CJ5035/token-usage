# 诊断报告（问题2）：「退出登录」物理删除该账号全部本地用量历史，不可恢复

- **日期**：2026-09-05
- **问题编号**：EVOLUTION-2
- **来源**：阶段0 探针C（操作流程与易用性），候选清单 `doc/20260905-evolution-candidates.md` #2
- **状态**：已确认（全部静态证据复核成立，且 EVOLUTION-1 落地后行为未变）
- **严重等级**：P1（损伤指数 7/10）
- **证据性质**：除标注 [推测] 外均为静态代码证据确认

---

## 1. 问题验证（当前代码仍存在）

| 探针主张 | 复核结果 |
|---|---|
| `clear_account` 物理删除该账号全部 usage_records 与 charts_buckets | **成立**。`app/db.py:715-732`（EVOLUTION-1 加锁后行号）：`DELETE FROM usage_records WHERE account_id = ?` + `DELETE FROM charts_buckets WHERE account_id = ?`，同时清 token、清空同步状态、`clear_cc_summary` |
| `/api/logout` 直通该函数 | **成立**。`app/server.py:1230` |
| 前端退出按钮与「重新登录」并排 | **成立**。`app/web/app.js:1738`：relogin / rename / logout 三按钮同排，logout 为 `btn-danger` |
| 确认弹窗披露了数据清除 | **成立**。`app.js:1778-1783` 确认后 `POST /api/logout`；i18n `logoutUserConfirm`（zh:85/en:197）："将退出「{name}」并清除其本地用量数据与同步记录，确定？" |
| 本地库是部分数据的唯一存档 | **成立**。`server.py:454-455`：`CC_MAX_PAGES` 注释"明细窗口固定最近 24h"——CommandCode 服务端仅保留约 24 小时明细；opencode 账号超出 `window_days`（默认 60，最大 3650）的历史同样无法重拉 |

**结论：问题仍存在。** EVOLUTION-1 仅为此路径加了锁（并发安全），未改变其删除语义。

## 2. 根因

**语义错位**：`clear_account` 的 docstring 把 `usage_records` 称为"本地缓存数据"（db.py:716），按"缓存可弃"模型设计退出；但对两类数据这不是缓存而是**唯一存档**：

1. CommandCode：服务端明细仅 24h 窗口，接入更早的历史只在本地；
2. opencode：超出同步范围 `window_days` 的历史，服务端不再返回。

而"退出登录"在用户心智中是**可逆操作**（登出→重登→一切恢复），"删除数据"的心智入口是「删除账号」。两套语义被合并进了退出路径。触发链：用户同步失败/会话失效 → 想点相邻的「重新登录」修复 → 误点红色「退出登录」→ 确认弹窗在"修同步"心态下被惯性确认（确认疲劳）→ 数据物理删除，重登也无法找回。

## 3. 用户体验影响

- **触发场景**：多账号用户修复会话/切换重登时的误触；确认弹窗虽有披露，但"清除本地用量数据与同步记录"的危害量级在"修同步"心态下被低估（确认疲劳），惯性确认。
- **后果**：退出→重登后，今日/7日/30日统计塌缩到 window_days 内可重拉的部分；CommandCode 账期汇总（cc_summary 已清）与 24h 前明细**永久丢失**；对以本地为账单存档的用户是灾难性且无声的（重登后界面正常，只是历史没了，用户可能数日后才发现）。
- **满意度预估**：不可逆数据丢失 + 发现滞后，是信任破坏最重的形态；确认弹窗的存在使责任归属模糊（"你确认过"），进一步损害信任。

## 4. 严重等级定级

**P1（7/10）**：后果是真实数据丢失（锚点 P0 区间），但有明确披露的确认弹窗兜底 + 触发需用户主动操作，降为 P1。影响面"中"（执行过登出的多账号用户）× 修复收益"高"。

## 5. 修复收益

- 消除唯一的"可逆操作导致不可逆数据丢失"路径；退出/重登成为真正的修复手段。
- 语义归位：退出=清凭证；删除账号=清数据（已有独立确认，`delete_account` 不动）。

## 6. 修复方向备忘（v2，供阶段3计划，非定稿）

### 方向A（推荐）：退出仅清凭证 + 数据保留 + UI 联动

1. **db 层**：`clear_account` 仅清凭证（token 置空、resolved_workspace_id=NULL）；`usage_records`/`charts_buckets`/`cc_summary` 与同步状态（含 total_records/last_sync_*）**全部保留**——同步状态保留使 `total_records` 展示（app.js:1394/1630）与留存数据一致。重登后无重复机制按"**幂等重拉**"表述（修正 v1 的"游标延续"错误表述）：增量同步无持久游标消费——opencode 从 page 0 拉起、连续两批 inserted==0 停止（server.py `_sync_one_account`）；bai/commandcode 翻页命中库内已有 usg_id 即停（server.py:466-467 docstring）；`usg_id TEXT PRIMARY KEY + ON CONFLICT DO UPDATE`（db.py:123/757）保证重拉无重复。`deepest_page_fetched` 为只写不读字段，重登路径 save_token 重置 -1 无碍。
2. **保留边界（prune 联动，须在计划中披露）**：`prune_old_records`（window_days，默认 60，可选"所有"=不裁剪）语义不变——保留的数据在用户自选保留窗内跨登出/重登存活，与"持续登录账号"同权；窗口外记录本就会被日常同步持续裁剪（v1"超出 window_days 的历史可保留"表述有误，如实修正）。CommandCode 的"服务端 24h × 本地 60d"缺口正是本地存档价值所在，方向A保住的是"退出/重登循环不再瞬间清零"。
3. **UI 联动（必须，否则语义分工不成立）**：
   - **列表放开过滤**：`renderUsersList`（app.js:1728）与用户菜单（app.js:1686）放开 `has_token` 过滤——未登录账号行保留显示，标注"未登录"徽标（复用现成 `t("notLoggedIn")` zh:64/en:176 与用户菜单 ：1697 的同款标注模式、`.badge.no` 样式），**行内状态后缀 `ur-ws` 的硬编码 `· ${t("loggedIn")}`（app.js:1746）改为随 `has_token` 条件渲染**（否则出现"未登录徽标+已登录后缀"并存）。
   - **删除入口**：非活跃行的现有「删除」按钮（复用 `deleteUserConfirm`"无法恢复"确认）成为登出账号的数据清除入口。活跃账号的清数据路径为两步：先退出（该行变为非活跃、删除按钮出现）→ 删除——此路径写入验收场景。共用电脑隐私路径 = 退出 → 列表仍见该账号 → 删除，列为显式验收场景。
   - **「登录」入口的定向落库（防凭证串号，v3 补）**：`save_token` 固定更新活跃账号（db.py:483-499）、`/api/relogin` 与 `open_login(mode)` 均不携带账号 id、switch 对无 token 账号返回 400"该账号未登录"——因此**非活跃未登录行的「登录」不能等价 relogin**。修法：登录意图携带目标 account_id——`/api/relogin` 增加可选 `id` 参数 → `pending_mode` 存储目标 id → 登录成功后定向落库（`save_token` 扩展可选 account_id 参数；main.py 的 add 分支已有带 dedupe_key 定向落库先例）。目标行=活跃行时行为与现 relogin 完全一致（活跃行仍是默认落库目标，clear_account 不移动 active 指针）。注意 `clear_account` 已清 `resolved_workspace_id`，定向落库的去重（workspace_hint）可能找不到旧行——此时按 add 分支的既有新建/去重逻辑走，旧行数据保留可见（与第 4 条边界一致）。
   - **最后账号退出的可达性（v3 补）**：`app.js:1789` 在无任何已登录账号时弹全不透明欢迎遮罩（仅「立即登录」「退出应用」），单账号形态下"列表仍见→删除"不可达。决策：遮罩增加次级入口**「管理本地数据」**（隐藏遮罩进入主界面并定位设置页，账号列表可见、可删；`/api/accounts` 等接口无登录门槛，可行），遮罩的强制登录引导条件（完全无账号行）不变。配套口径记录：账号卡片不再随登出即时移除（app.js:1788 改为保留行）；服务端 `/api/accounts/overview` 按 `has_token` 过滤（server.py:1071）的口径**保留**（概览面板只统计已登录账号，属合理业务口径）。
4. **视觉语义**：logout 按钮去掉 `btn-danger`、确认弹窗去掉 `danger:true`（新语义为非破坏性操作；保留红色将与"数据保留"文案矛盾、削弱其修复手段可用性），保留确认弹窗本身。**已知边界披露**：workspace_hint 为空时重登会新建账号行（main.py:540-543），旧数据归属旧行——放开列表过滤后旧行可见可管理，不再不可见。
5. **i18n 联动（实际范围）**：必改 `logoutUserConfirm`（zh:85/en:197）为"将退出「{name}」，仅清除登录凭证，本地用量数据保留"；新增/复用「管理本地数据」「登录」行级按钮的键（「登录」可复用死键 `goLogin` 或新键，plan 定夺）。死键清理附带项：`logoutConfirm`（:72/184）、`logoutDesc`（:30/142）、`reloginConfirm`（:71/183）、`reloginConfirmNew`（:86/198）均无 `t()` 调用，`logout`/`setLogout`（:30/142）语义重复——删除或保留由 plan 定。**后端硬编码中文**：switch 接口的"该账号未登录"（server.py）经 toast 直出（app.js:1713/1761 `e.message`），定向落库方案下该错误在正常流不可达，保持现状即可，但 plan 应记录该口径（若交互设计最终允许切换到未登录行，则必须映射为 i18n 键）。
6. **测试联动（行为变更）**：`tests/test_commandcode_db.py:334`（断言清除 → 改断言保留）、`tests/test_db_multiuser.py:247`（改为凭证级断言：token 清空、数据保留、作用域仍限活跃账号）、`tests/test_db_lock.py:223-227`（语义无关，复核即可）。新增：退出后重登（save_token 复用行）→ 记录仍在且同步续拉无重复的集成断言。

### 方向B（备选）：确认弹窗加"同时删除本地用量数据"勾选（默认不勾）

保留两种语义、服务隐私场景，与方向A可共存（A 保底 + 勾选服务显式清除意愿）；默认不勾对"误点+惯性确认"主场景零成本。代价：弹窗组件 + 后端参数 + 测试面翻倍。是否采纳由门禁2 权衡。

## 7. 范围声明

- 本问题改"退出登录"的语义、配套 UI 联动与文案；「删除账号」的删除行为与确认文案保持不变（现文案已含"无法恢复"）。
- 不涉及数据导出/备份能力（新功能需求，超出范围）。
- 不改 prune_old_records 的保留窗语义（用户配置的留存策略）。

## 8. 计划交接清单（门禁1 第 3 轮全部建议的固化，阶段3 必须逐项处置）
