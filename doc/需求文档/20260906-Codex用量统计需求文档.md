# Codex 用量统计集成需求方案

> 创建日期：2026-09-06
> 状态：待实施

## 一、需求概述

本需求中的“获取 token 秒速”统一解释为 token 生成速度（tok/s），不解释为首 token 延迟（TTFT）。参考 Codex session 日志只在存在明确单次请求耗时字段时才能计算真实 tok/s；当前参考格式通常没有该字段，因此当前版本必须正确显示 `—`，不得使用相邻请求间隔冒充生成耗时。

参考 `F:\GitHubs\zai-floating-monitor` 的 Codex 会话日志解析方式，在 GoGauge 中增加 Codex CLI 本地用量统计。程序读取本机 `~/.codex/sessions` 下的 JSONL 会话记录，解析 token 用量并纳入现有首页报表、统计页和记录页。

功能必须提供 Codex 用量总量、今日用量、按模型统计、按渠道统计，以及 token 生成速度（tok/s）指标。数据应支持增量读取、重复导入幂等、无 Codex 数据时的空状态展示，并与现有时间范围和渠道筛选保持一致。

## 二、参考实现与口径结论

参考项目的主要实现方式如下：

- 数据源为 `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`，支持通过环境变量覆盖 Codex 根目录。
- 会话扫描按稳定路径顺序执行；参考实现最多递归 3 层（年/月/日目录层级，见 `collect_session_files(&dir, 3, …)`），GoGauge 口径放宽为最多 5 层以兼容布局微调，并且不跟随符号链接或 junction（参考实现用 `path.is_dir()` 未显式排除符号链接，“不跟随”是 GoGauge 侧加固口径，不是参考实现既有行为）；目录不存在返回空扫描结果并由 `source_found` 区分“无目录”和“目录存在但无有效记录”。正式文件按文件名末尾 UUID 提取 `session_id`；无法提取 UUID 时退化使用不含扩展名的稳定 stem，并记录非阻塞告警，不使用 `session_meta` 作为主键来源。
- 环境变量优先级为 `GOUSAGE_CODEX_HOME` > `ZBAR_CODEX_HOME` > 用户目录下 `.codex`，取值均指向 `.codex` 根目录。`GOUSAGE_CODEX_HOME` 与 GoGauge 现有 `GOUSAGE_DATA` 命名族一致，作为主变量；`ZBAR_CODEX_HOME` 是参考项目实际支持的唯一会话目录变量（参考项目中不存在 `GOUSAGE_CODEX_HOME`），作为兼容回退。
- 用量来源按文件选择唯一模式，不能把两种事件同时计入：文件中存在有效 `token_usage_record` 事件时使用该模式，以非空 `response_id` 去重；文件中没有该事件时回退到 `event_msg` 且 payload 类型为 `token_count` 的兼容模式。`token_usage_record` 缺少 `response_id` 的事件视为格式错误，跳过并记录导入错误，不得生成无键记录或混入 `token_count` 模式。
- `token_usage_record` 模式每个 `response_id` 只生成一条用量记录；同一 `response_id` 重复出现时保留文件中最后一条完整事件的 usage，不做累加。其 `usage` 字段按与 `last_token_usage` 相同的输入、缓存读、缓存写、输出、reasoning 和总 token 字段映射。同一文件首次发现该模式时必须从头重建该文件，删除之前按 `token_count` 模式导入的记录。`token_count` 模式每条用量取 `info.last_token_usage`。
- `token_count` 的字段包括 `input_tokens`、`cached_input_tokens`、`cache_write_input_tokens`、`output_tokens`、`reasoning_output_tokens` 和 `total_tokens`；`cache_write_input_tokens` 当前样本恒为 0，但必须原样入库为 `cache_write_tokens`，不能丢弃未来格式提供的字段。
- 新版 Codex CLI（实测 2026-09 文件）会在同一请求前后重复发出 `token_count` 事件且 `last_token_usage` 完全相同，不去重会成倍多计（实测某会话 17 条事件直接求和为 993,748，真实累计仅 467,873）。`token_count` 模式下，与同会话上一条**有效** `last_token_usage` 五元组（input/cached/cache_write/output/total）完全相同的事件必须跳过；“上一条”状态必须跨批次持久化，不能因 offset 续读而丢失。该模式的请求数口径为去重后的用量事件数，并在响应中标记为近似请求数。实测重复事件的 `info.total_token_usage` 均不前进（本机 41/41），“total 不前进即跳过”与五元组相邻规则在现有样本上等效且可覆盖非相邻重复；本版本采用五元组相邻规则，total 判据保留为候选加固口径，出现非相邻重复样本时再启用。
- `token_count` 事件本身不带模型名，模型由同一会话中最近的 `turn_context.model` 归属；旧格式文件（实测 2026-07 及更早，本机 296/301 个）没有 `turn_context` 事件，模型只能记为 `unknown`，重扫也无法补齐。
- `session_id` 取自 rollout 文件名末尾 UUID（不依赖 `session_meta` 行——续读偏移后可能已越过该行）。`token_usage_record` 模式的唯一键为 `(session_id, response_id)`；`token_count` 模式的唯一键为 `(session_id, event_seq)`，其中 `event_seq` 是会话内 `token_count` 事件的顺序计数，包含被去重跳过的事件，日志行内仅部分新格式存在的 `ordinal` 不采用。上述键只在当前文件版本内稳定；文件发生重写、截断或采集模式切换时，必须在同一事务中删除该文件旧记录、重置进度并从头重建，不能靠 upsert 处理事件重排。增量续读在前缀指纹校验通过后，直接从进度表持久化的续读上下文（`event_mode`、`last_event_seq`、`last_token_usage_fingerprint`、`last_model`、`model_revision`）恢复，offset 只用于跳过已成功导入的完整行、只解析追加字节；指纹匹配已证明头部内容未变，持久化上下文与从头重扫的结果等价，不要求每次从文件头恢复。
- `provider_id` 与参考实现一致硬编码为 `codex`；`session_meta.model_provider` 实测恒为 `custom` 等抽象值，不能标识真实中转渠道，不用作渠道来源。

因此，Codex 记录全部归入 `codex` 渠道；不根据模型名称推导渠道。只有日志提供明确的请求耗时字段时才计算真实 tok/s（实测 603 条用量事件不含任何耗时字段，参考实现同样恒为 NULL）；否则不把相邻请求的时间间隔当作生成耗时，Codex 的速度值返回 NULL，界面显示 `—`。如果未来日志提供可可靠关联的耗时或流式事件，再以独立字段增加"事件间隔估算"，不与真实速度混用。

## 三、功能边界

### 包含范围

- 扫描 Codex 会话目录并增量解析 JSONL。
- 解析 `token_usage_record` 或兼容的 `token_count` 事件中的输入、输出、缓存、reasoning 和总 token，并按对应事件模式去重。
- 归属会话、模型、provider/channel、事件时间。
- 通过本地 SQLite 镜像表保存 Codex 记录和文件进度。
- 将 Codex 纳入现有自动同步流程和统计刷新流程。
- 统计总量、今日、当前时间范围、按模型、按渠道和每日趋势。
- 提供 token 生成速度字段，单位为 `tok/s`；只有日志包含明确单次请求耗时且样本有效时才显示数值，否则显示 `—` 并说明原因。
- 在首页统一渠道 Tab、渠道明细、趋势图、渠道占比和渠道概览中显示 Codex。
- 首页顶部总量、今日、输入、输出和请求等公共 KPI 必须与首页渠道明细使用同一合并口径，包含 Codex。默认 `/api/dashboard` 和不带 `scope` 的统计页请求保持现有 active-account 语义，不把 Codex 混入；首页显式请求 `/api/dashboard?scope=all&range=<range>` 时才返回全渠道 KPI，Codex 在报表层合并。Codex 没有账单费用，不计入费用合计，渠道明细中 Codex 费用列显示 `—`。
- 在统计页增加 Codex 专属统计区块。
- 在记录页增加确定的数据源筛选和 Codex 明细展示，保证采集到的数据可追溯。
- 更新关于页、欢迎页和页脚的数据来源与功能文案，反映 Codex 已接入。
- 支持 Codex 会话目录不存在、文件损坏、半行 JSON、字段缺失等降级场景。

### 不包含范围

- 不修改 Codex 原始 JSONL 文件。
- 不向 Codex 服务端发起额度查询或登录请求；本需求只统计本地会话日志。
- 不把 Codex 本地数据伪装成 OpenCode 账号，也不新增 Codex 登录凭证配置。
- 不承诺从现有日志推导真实 TTFT、真实网络耗时或单次响应生成时长；无明确耗时字段时不计算 tok/s。
- 不改造账户总览页的 OpenCode/BAI/CommandCode 账号模型；Codex 作为本地数据源接入公共渠道报表。
- 不在本阶段实现 Codex 远程同步、跨设备合并或云端备份。

## 四、核心实体定义

### `codex_usage`（本地镜像记录）

- **用途**：保存一条从 Codex session JSONL 解析出的用量事件；事件模式由 `event_mode` 标识，可来自 `token_usage_record` 或兼容的 `token_count`。
- **关键属性**：
  - `id: String` — 当前文件版本内的导入唯一键；`token_usage_record` 模式为 `codex:<session_id>:<response_id>`，`token_count` 模式为 `codex:<session_id>:<event_seq>`。文件重写或模式切换时旧记录会被删除重建，因此不承诺跨文件版本永久稳定。
  - `session_id: String` — rollout 文件名末尾 UUID 对应的会话标识。该标识为 rollout 文件级（与参考实现一致）：Codex Desktop 续跑同一对话会产生多个 rollout 文件，会话统计和 `session_count` 按 rollout 计数属预期行为而非缺陷；`token_usage_record` payload 自带 `thread_id`/`session_id`，未来如需对话级归并可另立字段，不改变本版本的键设计。
  - `event_seq: Integer|null` — `token_count` 模式下为会话内事件顺序计数（含被去重跳过的事件）；`token_usage_record` 模式为空。
  - `started_at: String` — 事件时间，统一存 UTC ISO 8601（与现有 `zcode_usage`/`claudecode_usage` 的 UTC ISO 存储约定一致）。
  - `model: String` — 最近一次 `turn_context.model` 归属的模型；旧格式文件无 `turn_context`，统一记为 `unknown`。
  - `provider_id: String` — provider/channel 标识，固定为 `codex`（与参考实现一致；`session_meta.model_provider` 为抽象值，不作渠道来源）。
  - `input_tokens: Integer` — 输入 token。
  - `output_tokens: Integer` — 输出 token。
  - `cache_read_tokens: Integer` — 缓存输入 token，日志中的 `cached_input_tokens`。
  - `cache_write_tokens: Integer` — 缓存写入 token，日志中的 `cache_write_input_tokens`。
  - `reasoning_tokens: Integer` — reasoning 输出 token。
  - `total_tokens: Integer` — 日志提供的总 token，一律以日志值为准（实测 603 条事件全部携带该字段；旧格式存在明细字段全 0 但总量有值的事件，不得用明细反推）；极端缺失时按 `input_tokens + output_tokens` 回退并计入最近导入错误。
  - `speed_tps: Real|null` — 仅在日志提供明确耗时字段时计算的 token 秒速；无明确耗时字段时为 NULL。
  - `duration_ms: Real|null` — 日志明确声明为该次请求耗时时原样保存；缺失或不满足有效性约束时为 NULL，不把事件间隔写入此字段。
  - `speed_source: String|null` — `duration` 或 NULL，用于说明速度来源。
  - `model_revision_at: Integer` — 模型上下文修订序号，用于 `token_count` 先于 `turn_context` 出现时补齐先入库的 `unknown` 模型记录；对旧格式文件无效（永远无法补齐）。
  - `event_mode: String` — `token_usage_record` 或 `token_count`，用于解释唯一键和请求数口径。
  - `response_id: String|null` — `token_usage_record` 模式的响应标识；`token_count` 模式为空。
  - `request_count_exact: Boolean` — 使用 `response_id` 去重时为 true，使用相邻 `token_count` 去重时为 false。
  - `cost_available: Boolean` — 当前固定为 false。
  - `file_path: String` — 原始 JSONL 文件路径，用于诊断和追溯（列名与现有 `claudecode_usage.file_path` 保持一致）。
  - `cost_raw: Integer|null` — 可选账单费用；Codex 日志通常没有费用，缺失时为 NULL，不按价格表估算。
  - `synced_at: String` — 写入 GoGauge 数据库的时间。
- **关联关系**：多条记录属于一个 `session_id`，按 `model` 和 `provider_id` 聚合。

### `codex_file_progress`（文件进度）

- **用途**：记录每个 rollout 文件的增量读取位置。
- **关键属性**：
  - `path: String` — 文件绝对路径，主键。
  - `file_size: Integer` — 最近一次成功扫描时的文件字节数。
  - `mtime_ns: Integer` — 最近一次成功扫描时的修改时间纳秒值。
  - `content_fingerprint: String` — 最近一次成功扫描范围 `[0, file_size)` 的 SHA-256 指纹；追加新日志时先比较当前文件前 `file_size` 字节的指纹，匹配则视为正常追加，不能因为完整文件的新指纹变化而重建。
  - `event_mode: String` — 最近一次成功扫描使用的事件模式。
  - `last_model: String|null` — 最近一次扫描恢复出的模型上下文。
  - `model_revision: Integer` — 模型上下文修订序号。
  - `has_turn_context: Boolean` — 文件是否出现过有效 `turn_context.model`。
  - `last_event_seq: Integer` — 已扫描到的 `token_count` 事件序号；包含因重复用量而跳过入库的有效事件，新增批次必须从该值继续。
  - `last_token_usage_fingerprint: String|null` — 最近一条有效 `last_token_usage` 五元组的稳定指纹，用于跨批次执行相邻重复去重；文件重写或模式切换时清空。
  - `parser_version: Integer` — 最近一次成功扫描使用的解析规则版本；解析规则升级导致解释口径变化时，旧版本进度失效并触发从头重建。
  - `offset: Integer` — 最后一条完整 JSONL 行的字节结束位置。
  - `updated_at: String` — 进度更新时间。
- **关联关系**：一个文件进度对应一个 JSONL 文件。文件变短，或文件长度不变且 `[0, file_size)` 指纹变化时，判定为重写；在同一事务中删除该文件对应的全部 `codex_usage` 记录、重置 offset 和事件序号，再从头扫描。文件变长且旧内容前缀指纹匹配时按正常追加处理，从 offset 继续扫描并复用持久化的续读上下文，不从头重扫；事件模式变化或 `parser_version` 过期时从头重建。修改时间变化本身不触发重建，只触发前缀/完整指纹校验；不依靠 upsert 修复事件重排。

### `codex_import_state`（导入状态）

- **用途**：持久化全局导入状态，保证应用重启后仍能诊断导入结果。
- **关键属性**：`last_import_at`、`last_success_at`、`last_error`、`scanned_directory`、`updated_at`。
- **运行状态**：`running: Boolean`、`revision: Integer`、`warning_count: Integer`；`revision` 仅在镜像记录或模型归属实际变化时递增，前端可用它判断后台导入完成后是否需要刷新。
- 导入失败只更新 `last_error`，不删除已有镜像数据；成功导入后更新 `last_success_at`。若本次扫描存在非法 JSON、字段缺失、无效时间戳等可跳过行，批次仍可成功提交，但必须将错误数量和文件路径保留为非阻塞告警；只有“无告警的完整成功”才清空 `last_error`，不能用成功写入部分数据覆盖告警。

### SQLite 迁移与批次原子性

- 首次创建和升级都必须通过幂等迁移（检查列/索引后再 `ALTER TABLE` 或 `CREATE INDEX IF NOT EXISTS`），不得删除或重建既有远程用量表；迁移失败时应用仍可读取旧数据，并在 `codex_import_state.last_error` 暴露错误。
- 单文件的“删除旧记录、重置进度、写入新记录和提交新进度”必须在同一 SQLite 事务中完成。批次提交失败时回滚记录和 offset，下一次从上一次成功的完整行继续，不能出现记录已写入但 offset 未推进或 offset 已推进但记录缺失。

### 采集器与批次接口

- `app/codex_api.py` 必须保持纯采集职责：模块导入不得扫描文件、访问数据库或启动线程；数据库写入由 `app/db.py` 批次提交函数完成。
- 采集器至少提供 `sessions_dir()`、`scan_session_files()`、`parse_session_file(path, progress)`、`import_incremental(progress, force=False)`、`normalize_usage(usage)` 和 `speed_from_duration(output_tokens, duration_ms)`。`parse_session_file` 从 `progress` 恢复 offset、事件序号、去重指纹和模型上下文后只解析追加字节；重建场景传入初始进度即从文件头解析。解析器以二进制字节 offset 为准，只推进到完整 JSONL 行末尾；末尾半行留待下次补全。
- `FileProgress` 必须同时保存 `offset`、`file_size`、`mtime_ns`、`content_fingerprint`、`event_mode`、`last_model`、`model_revision`、`has_turn_context`、`last_event_seq`、`last_token_usage_fingerprint` 和 `parser_version`。`FileBatch` 至少包含 `path`、`rows` 和更新后的 `progress`。
- `UsageRow` 必须保留 `id`、`session_id`、`event_seq`、`event_mode`、`response_id`、`started_at`、`model`、`provider_id`、`input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`reasoning_tokens`、`total_tokens`、`duration_ms`、`speed_tps`、`speed_source`、`request_count_exact`、`model_revision_at`、`cost_raw` 和 `file_path`。`cache_write_tokens` 不得由实现阶段固定为 0；缺失时才使用 0。`model_revision_at` 由采集器按发出记录时的当前模型修订序号填写，用于跨批次补齐 `unknown` 模型记录；`cost_available`（固定 false）与 `synced_at` 由数据库层在写入时填充，不属于采集器输出。
- 采集器应维护文件级 `last_scan_errors`，坏文件不阻塞其他文件；非法 JSON、缺失字段和无效时间戳属于可跳过告警，I/O、数据库和目录扫描失败属于导入失败。测试必须覆盖两种事件模式、重复导入、文件重写、模式切换、半行、坏文件与好文件并存、跨批次模型恢复、耗时字段、持久化上下文续读（指纹匹配后不从头重扫）和 `parser_version` 升级重建。

### CodexSummary（统计响应）

- **用途**：向前端提供 Codex 统计页和公共报表所需的聚合数据。
- **关键属性**：
  - `range: String` — `today`、`yesterday`、`7d`、`30d` 或 `all`。
  - `totals: Object` — 固定包含 `request_count`、`session_count`、`total_tokens`、`total_input_tokens`、`uncached_input_tokens`、`total_output_tokens`、`total_reasoning_tokens`、`cache_hit_tokens`、`cache_write_tokens`、`avg_tps`、`max_tps`、`speed_samples`、`speed_source`、`cost_usd` 和 `cost_available`；选择 `all` 时代表历史总量。
  - `today: Object` — 与 `totals` 使用相同字段结构，始终按本地自然日统计今日数据，且与首页今日 KPI 使用同一数据口径。
  - `channels: Array` — 每行固定携带 `provider_id`、上述 token/request/speed 字段以及 `cost_usd`、`cost_available`。
  - `models: Array` — 每行固定携带 `model`、`provider_id`、上述 token/request/speed 字段以及 `cost_usd`、`cost_available`。
  - `daily: Array` — 固定返回最近 7 个本地自然日（含今天，按日期升序）；每行固定包含 `date`、`request_count`、`total_tokens`、`total_input_tokens`、`total_output_tokens`、`cache_read_tokens`、`cache_write_tokens` 和 `total_reasoning_tokens`。`daily7` 为同一数组的兼容别名，不随 `range` 改变。
  - `totals`、`today`、`channels`、`models` 的聚合响应还应提供 `hit_rate`、`speed_samples` 和 `total_cost_usd`；Codex 当前费用字段均为 NULL，不得以 0 代替。
  - `db_found: Boolean` — 兼容字段，等于 `source_found || has_data`；不再用它区分目录缺失和历史镜像存在。
  - `source_found: Boolean` — 当前 Codex 会话目录是否存在。
  - `has_data: Boolean` — `codex_usage` 是否存在历史镜像数据；目录暂时不存在时仍保留历史统计。
  - `request_count_exact: Boolean` — 当前范围所有贡献记录都来自 `response_id` 去重时为 true；只要包含 `token_count` 兼容模式记录即为 false；范围为空时为 false，并由 `has_data` 区分“无数据”与“精确计数”。
  - `cost_available: Boolean` — 是否存在可用账单费用；Codex 当前固定为 false。
  - `cost_partial: Boolean`、`cost_unavailable_channels: Array<String>` — 全渠道聚合的费用完整性；Codex 有数据时属于不可用费用来源，但不影响 token/request 统计。
  - `last_import_at: String|null` — 最近一次导入时间。
  - `import_error: String|null` — 最近一次导入错误，供诊断展示。
  - `importing: Boolean`、`revision: Integer` — 后台导入状态和数据修订序号；summary 不等待后台扫描完成。

## 五、页面与接口影响范围

### 1. 首页：公共渠道报表

- 空数据和导入失败显示与其他本地数据源一致的状态。

涉及页面文件：

- `app/web/index.html`：记录页筛选控件和必要列。
- `app/web/app.js`：记录查询、来源筛选、Codex 字段渲染和分页。

### Codex 导入触发与登录独立性

- Codex 导入、`/api/codex/summary` 和 `source=codex` 的记录/会话查询必须独立于 OpenCode、BAI 或 CommandCode 登录状态；未登录任何远程账号时仍可读取 Codex 本地数据。显式 `source=all` 时合并全部已持久化的远程来源和本地镜像来源；省略 `source` 时才保留现状的 active account 兼容行为。所有接口仍遵循应用已有的本机访问控制，不新增绕过鉴权的公开入口。
- 应用启动后执行一次后台 Codex 增量导入。
- 访问 Codex summary、统一记录/会话接口和首页公共报表前，触发带节流和单飞保护的后台增量导入；不得在请求线程等待扫描完成。`/api/state` 或 summary 必须返回 `importing/running`、`revision`、最近错误和最近成功时间，前端在 `revision` 改变后刷新一次当前视图。
- 前端自动同步触发 `POST /api/sync` 时，在 `sync_usage` 账号同步后 piggyback 触发 Codex 增量导入（与 ZCode/Claude Code 一致；`sync_usage` 未登录时提前返回，未登录场景由启动导入与端点防抖覆盖），Codex 导入失败不得阻塞远程来源同步。
- 导入进度、最近导入时间、最近成功时间和最近错误必须写入 `codex_import_state`，并可供 summary 或诊断响应读取；导入过程不阻塞页面返回。

事件模式判定以文件级快照为准：首次扫描或重建时从文件头识别是否存在至少一条带非空 `response_id` 且 usage 完整的 `token_usage_record`，存在则整文件只使用该模式，否则使用 `event_msg`/`token_count`，判定结果持久化到 `codex_file_progress.event_mode`。增量续读信任持久化模式，只在追加字节中检测模式切换：`token_count` 模式下新增内容出现有效 `token_usage_record` 即判定切换，必须在同一事务中清理该文件镜像、清空 offset、`last_event_seq` 和 `last_token_usage_fingerprint` 后从头扫描；`token_usage_record` 模式下新增的 `token_count` 事件继续忽略，不得混入。模式判定、进度更新和记录写入必须使用同一文件版本快照。

### 实施顺序与验证门禁

实施按以下顺序推进，每个阶段完成后检查差异、相关测试和本需求映射，再进入下一阶段：

1. **T1 采集器**：实现路径定位、JSONL 完整行解析、两种事件模式、增量游标、指纹/重写保护和速度字段。
2. **T2 存储**：实现 `codex_usage`、`codex_file_progress`、`codex_import_state` 的幂等迁移、批次事务、导入幂等和 Codex 聚合。
3. **T3 服务与报表**：接入后台单飞导入、summary、`/api/state` 响应中的 `codex` 状态对象、六类公共报表和 `scope=all` 首页报表；保持默认 `/api/dashboard` 的 active-account 兼容行为。
4. **T4 统计页**：增加 Codex 专属统计区块、双语文案、空态、错误态、速度状态和后台 revision 刷新。
5. **T5 首页**：接入 Codex 渠道 Tab、全渠道 KPI、趋势、占比、单渠道概览和小时趋势；费用 NULL 不得渲染为 0。
6. **T6 记录与会话**：实现统一 `source` 筛选、记录/会话分页、跨来源稳定排序和 session 分组隔离；不新增 `/api/codex/records`。
7. **T7 本地访问与文案**：解耦远程登录与 Codex 本地可用性，更新中英文欢迎页、关于页、页脚和 README。
8. **T8 交付验证**：执行专项测试、相关回归、独立 fixture 服务、前端页面契约/浏览器检查和 PyInstaller 构建前置检查；验证结果必须来自实际命令或运行行为，不能以计划文本代替。

允许拆分为两个交付批次：**交付一** = T1–T5 与 T7（采集、存储、服务与报表、统计页、首页、本地访问与文案），**交付二** = T6（记录与会话统一）及其验证。拆分交付时，交付一阶段记录页不含 Codex 明细属已知边界，必须在交付说明中明示；T6 不得因拆分而取消，T6 实施前记录页维持现状行为。

阶段数超过 5 项时，实施过程启用逐项 checkpoint review；发现需求冲突时先暂停后续阶段，修订需求或计划后再继续，不得通过缩小验收范围规避冲突。

前端文案验收必须覆盖 `app/web/app.js` 的中文和英文文案字典，以及 `app/web/index.html` 中关于页、欢迎页和页脚的静态默认文案；不能只修改一种语言或只修改动态统计区块。

### 后端接口

#### `GET /api/codex/summary?range=<range>`

返回当前时间范围的 Codex 专属聚合。接口触发后台增量导入后立即返回缓存/已有数据，避免页面等待文件全量扫描。

#### `GET /api/codex/records`（不实现）

不新增 Codex 专用明细分页端点。记录页统一使用 `/api/usage/records?source=codex`，避免维护两套分页逻辑（现有代码中 ZCode/Claude Code 也只有 summary 端点，无 per-source records 端点先例）。Codex 明细字段包含模型、渠道、时间、token 明细、总 token 和 tok/s；当前日志没有明确耗时时 tok/s 为 NULL，前端显示 `—`。

#### 现有 `/api/usage/records` 与 `/api/usage/sessions`

统一响应中的 `key_name`、远程账单费用等 Codex 不适用字段返回 NULL，前端统一显示 `—`；已有来源的字段和筛选行为保持不变。统一记录增加 `source` 与命名空间后的 `source_record_id`；远程来源使用 `<source>:<account_id>:<native_id>`，本地来源使用 `<source>:<native_id>`，Codex 记录 ID 为 `codex:<session_id>:<response_id>` 或 `codex:<session_id>:<event_seq>`。

统一记录响应至少固定以下字段：`source`、`account_id`、`source_record_id`、`started_at`、`model`、`provider_id`、`session_id`、`input_tokens`、`output_tokens`、`reasoning_tokens`、`cache_read_tokens`、`cache_write_tokens`、`total_tokens`、`duration_ms`、`speed_tps`、`speed_source`、`cost_usd`、`cost_available`、`key_name`。远程 `created_at` 映射为 `started_at`；`usage_records.cache_write_5m_tokens + cache_write_1h_tokens` 映射为 `cache_write_tokens`；ZCode/Claude Code 的既有字段按各自镜像表映射；Codex 的 `account_id`、`key_name`、`cost_usd` 为 NULL，`provider_id` 固定为 `codex`。`cost_available=false` 时 `cost_usd` 必须为 NULL，不能把 NULL 渲染为 0。

两个现有接口新增 `source=all|opencode|bai|commandcode|zcode|claudecode|codex` 参数。`records` 返回统一明细字段，`sessions` 返回统一会话聚合字段；当 `source=codex` 时查询 `codex_usage`，当 `source=all` 时合并已有持久化来源并在 UNION 后统一分页。排序键固定为 `started_at DESC, source ASC, source_record_id ASC`，在同一查询快照内保证跨页稳定；后台导入使数据集发生变化时，前端刷新必须回到第 1 页，不能承诺 offset 分页跨导入快照绝对稳定。会话聚合优先按 `(source, account_id, session_id)` 分组，缺少 `session_id` 时回退到 `(source, account_id, key_id)`，两者都缺失时回退到按来源和账号的“未归属”分组，Codex 的 `account_id` 固定为 NULL 但仍按 `source` 隔离，避免不同来源或不同账号的记录被错误合并。Codex 不依赖 OpenCode 登录状态即可查询。

`sessions` 响应至少固定以下字段：`source`、`account_id`、`group_id`、`session_id`、`key_name`、`request_count`、`total_tokens`、`total_input_tokens`、`uncached_input_tokens`、`total_output_tokens`、`total_reasoning_tokens`、`cache_hit_tokens`、`cache_write_tokens`、`avg_tps`、`cost_usd`、`cost_available`、`last_at`。`group_id` 是分页和分组的内部稳定键，展示用 `session_id` 缺失时显示“未归属”；Codex 的 `account_id`、`key_name`、`cost_usd` 为 NULL，`cost_available=false`。会话费用同样遵守 NULL 不是 0 的规则。

#### 现有 `/api/report/*`

扩展现有公共报表的 Codex 数据源：

- `/api/report/windows`
- `/api/report/daily`
- `/api/report/hourly`
- `/api/report/channels`
- `/api/report/channel-overview`
- `/api/report/channel-trend`

所有接口的 `channel=codex` 和不传 channel 的全部渠道模式都必须支持 Codex，且范围、时区和合计口径一致。全部渠道响应必须同时返回按来源可解释的 `request_count_exact`、`cost_available` 和费用不完整标记；混合来源时按第七节规则计算聚合标记。接口读取统计前触发 Codex 增量导入；导入在后台执行时先返回已有镜像数据，下一次刷新显示新数据。

各接口必须按以下规则实现：

- `/api/report/windows`：Codex 纳入 today、yesterday、7d、30d 及同时段比较。每个窗口至少返回 `tokens`、`input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`reasoning_tokens`、`requests`、`cost`、`cost_available`、`cost_partial` 和 `request_count_exact`；Codex 的 token 使用 `SUM(total_tokens)`，`input_tokens` 原样保留日志输入（其中可能已含缓存读），`output_tokens` 原样保留日志输出（其中可能已含 reasoning），拆分字段只展示不再相加，费用未知时 `cost=null`。
- `/api/report/daily`：Codex 作为独立 `codex` series，支持 tokens、cost、requests 三种 metric。Codex 的 `tokens` 使用 `SUM(total_tokens)`；费用未知时不返回伪造的 0，`cost` metric 的 `series` **只包含费用可用的渠道**，Codex 不进入该对象，并在 `channel=codex` 时固定携带 `unavailable_channels=["codex"]`、`cost_available=false`；不传 `channel` 的全渠道响应按参与来源重新计算 `cost_available`、`cost_partial` 和 `cost_unavailable_channels`。`requests` 使用该文件事件模式定义的请求数。
- `/api/report/hourly`：Codex 按本地时区小时聚合，支持 today 和 yesterday，固定返回 24 个小时桶并补 0；每桶固定包含 `hour`、`input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`reasoning_tokens`、`total_tokens` 和 `requests`，其中 `total_tokens` 使用 `SUM(total_tokens)`，拆分字段不再相加。
- `/api/report/channels`：返回 Codex 渠道行，固定包含 `channel`、`tokens`、`input`、`output`、`cache_read`、`cache_write`、`reasoning`、`requests`、`cost`、`cost_available`、`cost_partial`、`request_count_exact`、`data_since` 和 `estimated`；Codex 无账单费用时返回 `cost=null`、`cost_available=false`、`cost_partial=true`、`estimated=false`，前端费用列显示 `—`。全部渠道费用只汇总 `cost_available=true` 的来源；混合结果必须额外返回 `cost_partial` 和 `cost_unavailable_channels`，不能把费用未知当作 0。
- `/api/report/channel-overview`：`channel=codex` 返回与 CodexSummary `totals` 同字段结构的聚合（费用字段保持 NULL/false）；默认首页总览 KPI 与渠道行使用相同合并口径，并按全渠道规则返回 `cost_available`、`cost_partial`、`cost_unavailable_channels` 和 `request_count_exact`。
- `/api/report/channel-trend`：`channel=codex` 返回 Codex 24 小时趋势；固定包含 `hour`、`total_input_tokens`、`total_output_tokens`、`total_reasoning_tokens`、`total_tokens`、`cache_read_tokens` 和 `cache_write_tokens`，其中 `total_tokens` 按小时 `SUM(total_tokens)`，避免把输入和已包含缓存/Reasoning 的输出再次相加。

首页顶部总量、今日、输入、输出和请求 KPI 实际由 `/api/report/windows`（全部渠道）和 `/api/report/channel-overview`（单渠道）驱动，合并 Codex 在上述 report 层完成；费用只合并有账单费用的来源，Codex 无费用不计入费用合计。默认 `/api/dashboard` 和不带 `scope` 的统计页请求继续服务 active-account 口径，不合并 Codex；首页如需全渠道 KPI，显式请求 `/api/dashboard?scope=all&range=<range>`，其 totals/today 必须复用 report 层合并结果，不能把“当前账号+Codex”伪装成账号统计。统计页的 Codex 数据由 `/api/codex/summary` 与专属区块提供，避免同一页面重复展示。不能只在前端渠道表中追加 Codex，否则首页 KPI、渠道明细和图表会互相不一致。

## 七、数据口径与异常处理

### Token 口径

所有 Codex 总量、今日、按模型、按渠道和首页公共报表中的“Token”字段统一按每条记录的 `total_tokens` 求和；输入、缓存读、输出、reasoning 作为拆分字段分别求和。这样可以避免缓存 token 在公共报表中漏计或重复计入。

- `input_tokens`：日志中的输入 token（实测已包含 `cached_input_tokens`）。
- `cache_read_tokens`：`cached_input_tokens`，单独展示，不与 `input_tokens` 相加（避免重复计入）。
- `cache_write_tokens`：`cache_write_input_tokens`，单独展示，不与 `input_tokens` 相加。
- `output_tokens`：日志中的输出 token（实测已包含 `reasoning_output_tokens`）。
- `reasoning_tokens`：`reasoning_output_tokens`，单独展示，不与 `output_tokens` 相加。
- `total_tokens`：一律以日志 `total_tokens` 为准——实测 301 个文件 603 条用量事件全部携带该字段；旧格式存在明细字段全 0 但总量有值的事件（290 条），任何“输入+缓存+输出+reasoning”式反推都会算错，参考项目同样无回退公式（直接透传日志值）。仅当极端缺失时按 `input_tokens + output_tokens` 回退，并计入最近导入错误供诊断。
- 统计按当前文件事件模式的去重结果求和：`token_usage_record` 按 `response_id` 去重，`token_count` 按相邻 `last_token_usage` 五元组去重；两种事件不能同时计入，也不把累计总量和单次增量同时计入。
- Codex 的 `tokens` 指标和所有 Codex 聚合统一使用 `SUM(total_tokens)`；现有其他渠道继续使用各自既有公式，全部渠道 UNION 时按来源分别计算后再合并，不能对合并后的拆分字段再次套用 `input + output + reasoning`。
- 混合来源报表的 `request_count_exact` 仅在所有参与来源都提供精确请求数时为 true；只要 Codex 使用 `token_count` 兼容模式，该聚合结果为 false，并保留各来源行的独立标记。

### 渠道口径

- 渠道固定为 `codex`（参考实现硬编码；`session_meta.model_provider` 实测恒为 `custom` 等抽象值，不作渠道来源）。
- 不使用模型名推导渠道，避免把 `gpt-5.3-codex` 等模型错误当成供应渠道。
- 只有 `codex_usage` 中存在至少一条有效记录时，首页渠道 Tab 和公共渠道明细才显示 `codex`；目录存在但没有有效记录时不增加空渠道。
- 前端渠道展示名称使用统一渠道映射，未知值 HTML 转义后原样显示。

### token 秒速口径

- 持久化字段为 `speed_tps`，聚合字段为 `avg_tps` 和 `max_tps`，并返回 `speed_source`。
- 只有日志提供明确的单次请求耗时字段（例如 `duration_ms`）、`duration_ms > 0` 且 `output_tokens > 0` 时才计算 tok/s，公式为 `output_tokens * 1000 / duration_ms`。
- `avg_tps` 是所有有效 `speed_tps` 的算术平均，`max_tps` 是有效样本最大值；NULL、零输出、非有限值、零或负耗时及计算结果非有限的样本不参与计算。不得使用未定义的“合理范围”静默裁剪；若未来需要上限，必须先新增明确常量和测试。没有有效样本时二者均返回 NULL。需要整体输出吞吐率时必须另设字段，不能将其混入 `avg_tps`。
- 当前参考格式没有明确单次请求耗时字段（实测 603 条用量事件无任何 duration 类字段，参考实现同样恒为 NULL）时，Codex 的 `speed_tps`、`avg_tps` 和 `max_tps` 返回 NULL，前端显示 `—`。
- 不使用相邻 token_count 事件之间的时间差作为默认生成耗时；未来如确认存在可靠的流式事件，再单独定义“事件间隔估算”字段和展示文案。
- 不新增 `avg_ttft_ms`，因为 Codex 日志无法可靠提供首 token 延迟。

### 异常处理

- Codex 目录不存在：返回 `source_found=false`。若镜像表已有历史记录，返回 `has_data=true` 和历史统计，同时在页面显示数据源当前缺失提示；只有目录不存在且镜像表无记录时才显示空态，公共报表不增加空渠道。
- 单行 JSON 非法：跳过该行并继续推进到下一条完整行。
- 文件末尾为半行：不消费半行，保留 offset 等待下次补全。
- 文件变短，或文件长度不变且旧内容前缀指纹变化：在事务中删除该文件旧记录并重置进度，从头重建；文件变长且旧内容前缀指纹匹配时按正常追加处理（复用持久化续读上下文，不从头重扫）；事件模式切换或解析规则升级（`parser_version` 过期）时从头重建。删除源文件本身不触发历史镜像数据清理。
- 模型上下文暂缺：记录可落库但模型显示 `unknown`。扫描时保存 `last_model`、`model_revision` 和 `has_turn_context`；当新格式中 `token_count` 先于 `turn_context` 出现时，使用文件路径和 revision 更新对应的 `unknown` 记录，并在同一事务中刷新相关聚合。旧格式文件（无 `turn_context`）永远无法补齐。
- 单文件读取失败：跳过该文件并记录最近一次导入错误，不阻塞其他来源同步。
- 导入失败：统计接口继续返回上一份可用数据或空结果，前端显示非阻塞错误状态。
- 非法 JSON、缺失 payload、空用量、非法/缺失时间戳、负数或非数值 token 字段均不得生成记录；完整行 offset 仍可推进，并按“可跳过告警”计数。文件级 I/O、数据库事务或目录扫描失败属于“导入失败”，保留上一份镜像数据并更新 `last_error`。
- 同一路径同大小的文件替换：每次决定复用 offset 前校验 `[0, file_size)` 的完整 SHA-256；指纹不一致即按文件重写处理。文件变长时先校验旧内容前缀，再只解析新增字节，并在本次成功扫描后保存新范围指纹。完整哈希校验只在一次导入触发中执行，不能以文件大小或修改时间单独判定内容未变化。

### 统一报表兼容范围

- 现有 DSH 不是持久化明细来源，继续只在首页公共报表的 today 窗口按当前实现追加；它不参加 Codex 记录页 `source` 白名单、不声称拥有历史 daily/hourly 明细，并将 `request_count_exact=false`（请求数不可用）。Codex 的加入不能改变 DSH 的既有发现、空态和 today-only 语义。
- “全部渠道”费用的 `cost_available` 表示是否存在可汇总账单费用，`cost_partial` 表示结果同时包含有费用和无费用来源；当窗口有 token/request 数据但所有参与来源费用都未知时 `cost=null`，空窗口才可返回 `cost=0`。Codex 当前固定 `cost_available=false`，有数据时 `cost_partial=true`，且不参与费用合计。

- 解析合法 `token_usage_record` 和 `token_count` 事件并正确映射输入、输出、缓存读、缓存写、reasoning 和总 token 字段。

- 明确耗时 tok/s 的有效样本、异常样本和无样本结果符合口径；当前无明确耗时时返回 NULL 并显示 `—`。

## 九、注意事项

- 本文不假设工作区干净，也不把当前 git 状态作为功能前置条件；实施开始前必须重新执行 `git status --short`，保留其他任务的修改，不能按历史文档中的“已提交/无未提交”描述覆盖文件。
