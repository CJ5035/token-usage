## 1. 背景与问题

随着接入渠道增多（OpenCode → BAI → CommandCode，后续可能继续增加），当前面板的统计视角出现缺口：

| 现有页面 | 统计视角 | 缺口 |
|---------|---------|------|
| 首页 home | 单账号：配额窗口 + 用量概览 + 24h 趋势 | 只看当前选中账号 |
| 统计页 stats | 单账号：Token 构成 / 模型用量 / 30 天趋势 | 只看当前选中账号 |
| 账户总览 overview | 跨账号：今日合计 + 账号卡片 + 7 日费用对比 | 以"账号"为粒度，无渠道维度；仅 7 天；无 Token 维度的全局汇总 |

**用户核心诉求**（v2 确认）：**每次打开应用，第一屏就看到所有渠道合计的总量**；想看某个渠道时，再主动切到该渠道。即"默认全局、下钻分渠道"。

具体要回答三个问题：
1. 今天/本周/本月我一共烧了多少 Token？花了多少钱？
2. 这些消耗分布在哪些渠道上？各占多少？
3. 趋势如何？哪天用得最多？哪个渠道增长最快？

## 2. 数据基础盘点（可行性）

跨渠道聚合的数据基础**已经存在**，无需新采集：

- `usage_records` 表统一存储三渠道记录：`account_id`、`provider`（opencode/bai/commandcode）、`model`、`created_at`、`input_tokens` / `output_tokens` / `reasoning_tokens` / `cache_read_tokens` / `cache_write_*`、`cost_usd`
- 三渠道写入路径均已落地：`insert_usage_records`（15 处调用，含 bai_sync / commandcode_sync）
- 前端已有 Chart.js（`chart.umd.min.js`）、时间范围 pill 组件、KPI 卡片、堆叠柱状图（7 日趋势对比）等可复用件

**口径注意**（方案各处需显式标注）：
- OpenCode：官方 cost，精确
- BAI：本地定价表**估算**成本（前端已有 `est-badge` 估算标记，沿用）；**cost_usd 写入时固化，定价表更新不回溯历史记录**（v8 明确：用户更新定价表后历史费用不变，属预期行为）
- CommandCode：官方 cost；另有账期口径快照（cc_summary，不并入日趋势，避免双口径混淆）
- ⚠️ **渠道维度必须取 `accounts.source`，不能取 `usage_records.provider`**（v4 查证）：OpenCode 记录的 provider 是模型商（anthropic/openai/google…，opencode_api.py:462），仅 BAI/CmdCode 写渠道名。按 provider 分组会把一个 OpenCode 账号拆成十几个"渠道"。正确做法：`usage_records.account_id` JOIN `accounts.source`（该列有迁移兜底，db.py:226-229）。
- 时区：现有统计统一 `datetime(created_at,'localtime')` + `date('now','localtime')`（db.py:1223 有现成 RANGE 条件映射表），新聚合 SQL 直接复用，不另造。

**要点**：
- **环比同时段口径（v4）+ 样本保护（v5）**：今日是未完成天，不与昨日全天比——今日截至 14:00 对比昨日截至 14:00；"变橙"阈值同理为"今日同时段 > 过去 7 天同时段均值 × 2"，其中**"过去 7 天"= 近 7 个完整自然日（不含今天）**（v6 明确，避免今天自己除自己）。**最小样本保护：当前时刻 < 01:00 或对比窗口记录数 < 5 条时，副行显示"样本不足"，不显示百分比**（防凌晨环比爆炸 +9999%）
- **窗口条固定性（v6）**：固定 4 窗口（今日/昨日/近7天/近30天），不随页头范围 pill 变化；二者职责不同——窗口条是"免切换的总量速览"，pill 控制图表区与明细表
- **请求数口径（v6）**：请求数 = `usage_records` 行数（三渠道一致：一行 = 一次调用）
- **历史深度标注（v4 定，v8 措辞修正）**：各渠道接入/同步深度不同（同步范围 30/60/90/180 天可配），涉及超深度范围时按渠道标注"数据自 X 日起"（取 `usage_sync_state.oldest_record_at` 现成字段）。取值规则：**明细表每渠道行 = 该渠道内多账号的 min(oldest_record_at)；窗口条合计标注 = 全部渠道账号的 min**；明细表加"数据自"列
- **数据新鲜度（v4 定，v10 归并规则补全）**：配额摘要条每渠道带"最后同步时间"（取 `usage_sync_state.last_sync_at`）。**同渠道多账号归并规则：取 min(last_sync_at)——最陈旧账号优先**（取 max 会让"2 分钟前"掩盖另一账号 1 小时未同步）；**任一账号 `last_sync_status != success` 即显示红点⚠**（失败优先于新鲜度）；避免用户把旧数据当实时
- **配额摘要条口径（v5）**：BAI 积分 / CmdCode USD 余额跨账号**合计**；OpenCode 窗口百分比不可合计，显示**最紧张账号 max% + 账号数角标**（如 `82% · 2账号`）
- 堆叠图是核心图表：一根柱子 = 一天全渠道总量，分段 = 各渠道，同时回答"总量"与"分布"
- 费用含 BAI 估算值时，总费用 KPI 沿用 `est-badge` 标记；**指标 seg=费用时，堆叠图/环形图标题处同样显示估算标记**（v6）
- 渠道配色固定映射（opencode=blue / bai=amber / commandcode=violet）写入 CSS 变量，全应用统一

### 3.2 渠道统计页（降级为 P1 可选）

v2 后，渠道 tab 已覆盖"看单个渠道"的主诉求。独立渠道统计页仅在以下场景仍有增量价值，放 P1 视使用反馈决定：

- **渠道横向对比**：渠道卡片列（配额 + 当日消耗 + 7 日 sparkline）+ 分组柱状对比图
- **渠道效率对比表**：平均每请求 Token / 平均每请求费用 / 缓存命中率 / 最常用模型 —— 回答"哪个渠道最划算"，指导任务路由

### 3.3 导航与排版（v2：导航零改动）

**左侧导航不加任何项**：

```
  ⌂  总览(首页)  — 落地页; 页内渠道 tab: 全部(默认)/各渠道
  📊 统计       — 保持原样 (单账号深度分析; 后续再议是否并入)
  📄 使用记录    — 保持原样
  👥 账户总览*   — 保持原样 (账号粒度, 与渠道粒度互补)
  ⚙  设置 / ℹ 关于
```

- 「全部 vs 分渠道」是同一数据的**视角切换**，用页内 tab；左侧导航是**页面跳转** —— 两者心智不混用，这是本方案不新增导航项的理由
- tab 控件样式复用现有 pill-row（与 mr-dim 模型维度切换一致），零新组件成本
- 渠道数 > 5 时 tab 自动折叠为下拉（预留，当前 3 个渠道无此问题）

## 5. 技术实现概要

- **新增 API**（server.py，均为只读聚合 SQL，不动写入路径）：
  - `GET /api/report/windows?channel=` → 时间窗口汇总条：today / yesterday / 7d / 30d 四窗口各返回 tokens/cost/requests + **同时段环比**（今日截至当前 vs 昨日同时段、vs 7 天同时段均值；样本不足时返回标记而非百分比）+ **各渠道数据深度**（oldest_record_at）+ **各渠道最后同步时间与状态**；channel 缺省 = 全部渠道
  - `GET /api/report/daily?range=today|yesterday|7d|30d|all&channel=&metric=tokens|cost|requests` → 按日 × 渠道堆叠序列（跟随图表区 5 档 pill + 指标 seg；v5 增加 yesterday 档，RANGE 映射加一行）；range=all 时服务端粒度自适应（>60 天按周 / >180 天按月）
  - `GET /api/report/hourly?date=&channel=` → 24h × 渠道堆叠序列（仅"今天/昨天"范围）
  - `GET /api/report/channels?range=` → 渠道明细表（全部 tab 底部，含各渠道 oldest_record_at，跟随图表区 pill）
  - 渠道 tab 列表：`DISTINCT accounts.source`（有账号的渠道才出现）
  - 单渠道 tab 的配额/概览数据复用现有 dashboard 接口 + 按 `accounts.source` 过滤，不新造；**dashboard 复用接口的 range 参数随 db.py:1223 RANGE 映射同步支持 yesterday 档**（v6：页头 5 档 pill 对单渠道 tab 同样生效，复用接口不得只认旧 4 档）
- **核心 SQL 模式（v4 修正：渠道维度 = accounts.source，JOIN 获取）**：
  ```sql
  SELECT substr(datetime(r.created_at,'localtime'),1,10) d,
         COALESCE(a.source,'opencode') ch,
         SUM(r.input_tokens + r.output_tokens + r.reasoning_tokens) tokens,
         SUM(r.cost_usd) cost, COUNT(*) reqs
  FROM usage_records r LEFT JOIN accounts a ON a.id = r.account_id
  WHERE r.created_at >= ?            -- 范围, 复用 db.py:1223 RANGE 条件映射
    AND (? IS NULL OR a.source = ?)  -- 渠道过滤
  GROUP BY d, ch
  ```
  ⚠️ 禁止 `GROUP BY provider`：OpenCode 记录的 provider 是模型商（anthropic/openai…），仅 BAI/CmdCode 写渠道名（v4 已查证 opencode_api.py:462 / bai_api.py / commandcode_api.py:285）。
  LEFT JOIN + COALESCE 仅为防御迁移期数据：**删账号会级联删除 usage_records**（v6 已查证 delete_account，db.py:616-623），正常无孤儿记录；v2.0 多用户前的老数据兜底归 'opencode' 恰好正确。
  时区与范围（v7 口径）：自然日相关统一 `datetime(created_at,'localtime')` + `date('now','localtime')`。**新聚合 API 的范围窗口一律用自然日**：today=`= date('now','localtime')`、yesterday=`= date('now','localtime','-1 day')`（新造子句）、7d=`>= date('now','localtime','-6 days')`（含今天共 7 天）、30d=`-29 days` 同理——与按日分组的堆叠图严格对齐，保证窗口条合计 = 柱子之和。⚠️ **不直接复用 `_period_where` 的 7d/30d**：其实现是滚动 `datetime('now','-N days')`（db.py:1237），属 stats 页历史口径，P0 不动它。
  三个"7 天"口径并存且各自明确（v7）：窗口条"近7天"= 含今天的 7 个自然日（与堆叠图对齐）；环比均值 = 近 7 个**完整**自然日（**不含今天**）；stats 页"近7天"= 滚动 7×24h（历史行为，不动）。
  同时段环比：今日窗口取 `created_at <= now`，昨日对比窗口取 `昨日 00:00 <= created_at <= 昨日同时刻`（SQL 用 `time(created_at,'localtime') <= time('now','localtime')` 过滤）；7 天同时段均值 = 近 7 个完整自然日（不含今天）各日同时段之和 / 7。
- **前端**：app.js 改造 `page-home`：页头加渠道 tab 控件（复用 pill-row 样式）；`loadDashboard` 按 `state.channel` 分支渲染（全部=新聚合视图 / 单渠道=现逻辑+过滤）；**首页与顶栏 user-switch 解耦**（v4：首页纯渠道维度，user-switch 仅影响账户总览/记录等页——实施时确认现有 user-switch 的联动点并摘除首页挂钩）；图表复用 Chart.js 与现有配色常量；i18n key 新增约 35 条
- **配额摘要条**（全部 tab）：数据源复用 **`_quota_cache`**（server.py:57，按账号缓存 + `_ensure_quota_async` 异步刷新 + 防重入，三渠道 fetch 齐备，v2.1.0 账户总览同款机制）。**实现模式（v8 已查证 server.py:195 为单账号粒度）：遍历所有账号逐个 `_ensure_quota_async(aid)`（过期才后台刷新、防重入），同步读 `_quota_cache` 归并；首刷账号的配额异步返回，摘要条先显骨架/旧值，与账户总览面板行为一致**——不新造轮询；归并规则：BAI 积分/CmdCode USD 合计，OpenCode 取最紧张账号 max% + 账号数；同步时间与状态取 `usage_sync_state`
- **24h 图口径（v5）**：现首页单账号用 `db.today_trend()`（server.py:788）；全部 tab 的 24h 堆叠用 usage_records 跨渠道小时聚合，代码注释区分两种口径。范围≠今天时 P0 先隐藏（有布局跳动），**P1 改为时段画像**（范围内所有天按小时聚合，仅换 GROUP BY）
- **性能**：聚合 SQL 在 `created_at` 已有索引 + JOIN accounts（小表）前提下毫秒级；窗口条 4 窗口用一次扫描 + CASE WHEN 条件聚合，避免 4 次全表扫；范围"全部"且数据量超 10 万行时可加 `daily_summary` 物化表，P0 不做
- **实施前置验证（v5）**：三渠道 `created_at` 均为官方原样透传，格式未必统一（带不带 Z、有无毫秒）——实施第一步跑验证查询确认 sqlite `datetime(created_at,'localtime')` 对三种格式解析正确，结果固化进测试
- **实施顺序（v5，两个 commit）**：① 后端 4 个聚合 API + `test_report_api.py`（SQL 口径可独立验收）② 前端首页 tab 改造（含 user-switch 解耦）
- **测试**：tests/ 新增 `test_report_api.py`（沿用现有 test_db_multiuser.py 的多账号 fixture 模式），覆盖：跨账号跨渠道聚合正确性（**重点：OpenCode 记录 provider 为模型商时仍按 source 归一**）、channel 过滤、同时段环比边界（凌晨 0 点样本不足、跨月）、**自然日窗口边界（7d 首日完整性：窗口条近7天合计 = daily 接口 7 根自然日柱子之和）**、范围=all 粒度自适应、oldest_record_at 透传、三渠道 created_at 格式解析、空数据、BAI 估算标记透传
