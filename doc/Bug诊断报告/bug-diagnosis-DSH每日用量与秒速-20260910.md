# DSH 每日用量与秒速诊断

- 日期：2026-09-10
- 状态：代码与本机日志已验证，尚未修改产品代码
- 严重级别：P2（统计能力缺口与速率口径错误）
- 范围：DSH 本地日志解析、首页报表、统计页

## 问题与结论

用户希望 DSH 与其他渠道一样具备每天用量、token 秒速。现存日志提供了时间戳和 token 数据，技术上可以补齐；当前只实现总量/今日桶，通用历史报表没有接入 DSH。秒速已有后端计算和统计页显示入口，但首页渠道概览未提供此指标，计算还存在无效样本污染分子的缺陷。

## 验证证据

2026-09-10 20:03 本机只读执行 `dsh_api.scan()`：发现 440 个会话文件，扫描约 3.69 秒。今日输入（含缓存）88,184,407，输出 578,712，当前算法 tps 128.17。此速率仅证明计算链路有值，因下述分子缺陷，不能作为修正后真实速率。

遍历现存日志的 assistant/message usage：14,492 条，分布于 24 个有记录的自然日，最早 2026-08-13、最晚 2026-09-10；这些消息未发现缺少时间戳或 turn/step。消息数是原始事件计数，并非已去重的请求数；没有记录的日期不能据此断言没有使用，删除的日志不能恢复。

基线：`python -X utf8 -m pytest tests/test_dsh_api.py tests/test_dsh_background.py -q`，31 passed。

## 调用链与影响

`~/.dsh/sessions/*/*/session.jsonl.zstd` → `decompress_frames` → `stat_log`（按 turn:step 去重、步骤计时）→ `scan`（总量/今日聚合）→ `get_dsh_usage`（后台缓存）。

统计页：`/api/dsh/usage`（app/server.py:1608）→ `loadDshUsage`（app/web/app.js:1083）→ `renderDsh`（1109）。

首页：缓存 → `_report_windows_response`（app/server.py:1315）、`_report_channels_response`（1354）、`_dashboard_all_payload`（1391）、channel-overview 分支（1830）。历史 daily/hourly/channel-trend 则直接调用 db，所以没有 DSH。

影响范围：解析缓存结构、报表聚合、DSH 专用区块、范围切换/主题/语言重渲和对应测试。数据库层保持不依赖 dsh_api，避免循环依赖。

## 边界检查

| 场景 | 当前行为/风险 | 建议 |
|---|---|---|
| chunk/message 重复 | 同一步后到覆盖 | 保持去重，分桶必须在去重后进行 |
| 缺少/异常计时、短输出、超限速率 | token 照计，秒数剔除；速率分子未剔除 | 有效输出与有效秒数同时累计，无样本显示 — |
| 跨午夜、跨日步骤、未来时间戳 | 今日只检查 >= 本地零点，无上界 | 按完成时间归属自然日；范围使用明确上下界；冻结单次查询时钟 |
| 缓存跨午夜 | 缓存里今日桶会陈旧 | 缓存保存带日期的原始统计，查询时按当前自然日选桶 |
| 多请求、范围快速切换 | 共享缓存；DSH 无序号守卫 | 查询只读，不修改缓存；范围请求加序号防旧响应覆盖 |
| 正在写入/截断日志 | 丢弃未完成帧 | 保持容错，下次扫描补齐 |
| 冷启动、无目录、刷新失败 | 空态与扫描中混淆，保留 stale | 显式扫描状态，页面可见时有界重试，失败保留快照 |
| 缓存 token | input 已含 cache；cache 合并读写 | 总 token 不重复加 cache；报表读写列需分开保存 |
| 费用、请求数 | 日志无费用；步骤数不保证等于 HTTP 请求数 | 未知费用显示 —；保留步数标签与精确度标志 |
| 历史对比 | DSH 今日值可参与分子，但历史比较不含它 | 同时段两侧统一来源；无法对齐时标记不具备比较条件 |
| 性能 | 本机全扫描约 3.69 秒 | 一次后台扫描复用各范围，不为每次筛选重新解压 |

## 建议

按配套《20260910-DSH每日用量与秒速对齐实施计划》实施。历史能力只承诺现存日志范围；秒速定义为平均输出 token/s（步骤输出 / 步骤耗时，含等待等开销），不称为实时瞬时生成速度。
