| 前端 fetch 无超时/无中止 | **成立**。`app/web/app.js:313-321`：`fetch` 无 AbortSignal/timeout；后端冻结多久 UI 骨架屏多久，无反馈无重试 |

**结论：问题仍存在。** 探针定级依据中的"ZCode 15s 常态阻塞"已被预热收窄为竞态窗口/预热失败场景；汇率阻塞为 6h 一次的 10s 冷块。

## 2. 根因

三类"网络等待"被放在了用户可感知的同步路径上，且失败无用户可见反馈：

1. **汇率**：请求线程内同步外呼（10s 上限）。设计上汇率是展示性数据（有默认值 7.2 兜底），不该阻塞统计主链路。
2. **ZCode 配额冷首采**：同步首采是 7 项修复时"打开页面即有数据"的取舍；预热覆盖常态后，残留风险是竞态窗口内的**并发缓存击穿**（N 个并发首请求 = N 次完整 15s 外呼）。
3. **前端无超时**：fetch 默认无限等待，任何后端慢都被放大为"无反馈冻结"，用户无重试入口。

## 3. 用户体验影响

- **触发场景**：① 冷启动/弱网/被墙环境下首次打开首页——骨架屏最长 10s（汇率）；② 预热未完成或预热失败时首次进 zcode 页签——最长 15s；③ 任何后端异常挂起——前端永久等待。
- **后果**：等待期间无进度、无取消、无错误提示；冻结结束后无任何解释。用户归因为"软件卡死"。[推测] 满意度影响集中在弱网/离线用户的首启动体验（本地工具的核心人群在国内访问 open.er-api.com / GLM 端点，弱网概率不低）。

## 4. 严重等级定级

**P2（5.5/10）**：明显体验折损（长等待无反馈）但可完成、有预热/兜底缓解、低频触发。不到 P1（核心功能不受阻）。与探针 6.5 的差异：预热与失败缓存已落地，触发面收窄。

## 5. 修复收益

- 消除首页与 zcode 页签的同步网络阻塞；请求路径变为纯内存读（毫秒级）；并发首采击穿收敛为单次外呼。
- 前端加超时 + **失败可见化**（v2 补：仅超时不足——dashboard 失败 catch 现状只 console.error、骨架屏永久残留 app.js:545-548，需配套错误占位与重试入口）后，后端慢/挂从"无反馈冻结"变为"可理解错误 + 可重试"（防错+错误恢复）。
- **用户可感知语义变化（须在计划中写明，避免被当回归误报）**：汇率后台化后，弱网冷启动首屏立即显示兜底值 7.2（原行为阻塞最多 10s 换实时值），后台刷新到位后下次拉取更新。

## 6. 修复方向备忘（v2 定稿，供阶段3计划）

- **方向A（后端去阻塞）**：
  1. **汇率后台化（惰性触发模式，不引入常驻定时线程）**：启动时后台线程预热 `_fetch_usd_cny`（复用 `zcode_quota_warmup` 的既有线程模式）；6h TTL 过期后由**请求路径发现过期 → 触发后台刷新 → 本次返回旧值**（与 `_ensure_quota_async`/`_ensure_zcode_quota_async` 的既有惰性模式一致）；请求线程永不外呼。失败保留"缓存旧值 6h"语义。
  2. **ZCode 冷首采严格单飞（定稿：等待同一拉取）**：`_zcode_quota_payload` 的 `data is None` 同步首采路径用 `threading.Lock` 包裹 check-and-set + 进行中标记：并发首请求**等待同一拉取完成**（带超时兜底 ≈ QUOTA_TIMEOUT + 2s 余量，防拉取线程意外终止时等待者永久挂起），拉取完成后共享同一结果——保持"首次同步返回数据"产品语义不变，杜绝 N×15s 击穿。~~"快速返回加载中占位"~~不采纳（推翻保留语义且需前端配套，收益低）。
- **方向B（前端超时 + 失败可见化，v2 扩充）**：
  1. `api()` 加 `AbortSignal.timeout(20000)`（signal 置于 `...opts` 展开前保留调用方覆盖；加 `typeof AbortSignal.timeout === "function"` 守卫，不支持时降级为现状不超时；WebView2 Chromium 103+ 已确认支持）。
  2. `api()` 层识别 `e.name === "TimeoutError"` → 抛出带 i18n 文案的错误（新增键 `requestTimeout`：zh"请求超时，请检查网络后重试"/en"Request timed out. Check your network and retry."）。
  3. **失败可见化落点（v2 新增，否则超时收益不可达）**：`loadDashboard` 的 catch（app.js:545-548，现状只 console.error）渲染错误占位行并提供「重试」按钮（重调 loadDashboard）；`loadZcodeQuota` 失败静默隐藏（app.js:693-701）补一条 toast。与备选池"错误恢复链路断裂"同源，本次仅覆盖 dashboard 与 zcode quota 两个现场，其余留备选池。
- **不改动**：`_zcode_quota_payload` 的"首次同步返回数据"产品语义保留；失败缓存 6h 语义保留；同步引擎网络超时不动。

## 7. 验证场景（阶段3计划须包含，PM 席要求）

1. 断网冷启动打开首页：骨架屏 <1s 消失，汇率显示兜底值 7.2，无冻结。
2. 并发进 zcode 页签（预热未完成）：仅 1 次外呼（单飞生效），全部请求共享结果，无 N×15s。
3. 正常网络回归：汇率与配额数据正确；dashboard/zcode 渲染无回归。
4. 前端超时路径（模拟后端挂起）：约 20s 出现"请求超时"可理解提示，dashboard 出现错误占位 + 重试按钮，点击重试可恢复。

## 8. 范围声明

- 不改动同步（sync）引擎的网络超时（各 api 模块已有 10~20s，探针确认无问题）。
- 前端超时只加在通用 `api()` 一处，不做分端点差异化配置；统一 20s 阈值与最长端点（zcode 15s + 单飞等待余量）的匹配在计划中复核。
- 离线模式的完整产品化（离线标识/降级提示）超出范围。
- 错误恢复入口不对等（dashboard 有重试、zcode 仅 toast 无恢复入口）→ 显式归属备选池"错误恢复链路断裂"。
- 错误恢复交互的全面治理（retryTip 文案、其余页面失败态）属备选池"错误恢复链路断裂"，本次仅覆盖 dashboard/zcode quota 两个现场。

## 9. 计划交接清单（门禁1 第 2 轮全部建议的固化，阶段3 必须逐项处置）

1. **单飞原语统一**：预热 worker 与请求路径的冷首采统一走同一单飞函数（当前 `_ensure_zcode_quota_async` 的 worker 不经 `_zcode_quota_payload` 同步路径，预热与首请求可能各发一次外呼）——统一后 §7 场景 2 判据"仅 1 次外呼"严格成立。
2. **等待者超时行为定死**：等待锁超时（≈17s）后返回错误占位（对齐 fetch_quota 错误 dict 形状）并入队后台刷新；**不得降级为等待者自行再拉取**（17s+15s=32s 会撞前端 20s 阈值）。
3. **阈值复核判定线**："A.2 等待兜底 + 本地往返 < 前端 20s"；调整 QUOTA_TIMEOUT 或等待余量时同步复核前端阈值。
4. **错误占位覆盖范围**：`renderSkeletons`（app.js:474-484）渲染 5 个区域——错误态下**全部骨架区域替换为错误占位（或清空）+ 单一重试入口**，禁止"一块错误 + 其余骨架"的半死状态。
5. **zcode toast 文案**：复用现成键 `zcodeQuotaFail`（zh:90/en:200），不新增；随键注明零打扰语义（无凭证用户走错误 dict→引导框路径，不进 catch，toast 不打扰无订阅用户）。
6. **重试按钮 quiet 语义**：重试以正常路径重调 loadDashboard，再失败再次渲染错误占位（反馈方式幂等，不跳变 toast）——计划细化。
7. **行号勘误**：汇率 TTL 定义实为 server.py:64（:65 为 _DEFAULT_USD_CNY）；dashboard catch 还含 `showLoading(false)`（app.js:546），"无错误占位/无重试/骨架残留"实质不变。
