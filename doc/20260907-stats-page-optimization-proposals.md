# page-stats（用量统计页）优化方案对比

**文档编号**: 20260907-stats-page-optimization-proposals  
**创建日期**: 2026-09-07  
**改造对象**: page-stats（用量统计页）

---

## 当前问题分析

### 现状

page-stats 包含以下内容：
1. **全局汇总**：总请求数、总 Token、总费用、平均命中率（跨所有数据源）
2. **Token 构成**：输入/输出/推理/缓存读的占比
3. **模型用量**：各模型的 Token/费用排行
4. **用量趋势**：按日期的折线图
5. **本地数据区块**（独立展示）：
   - ZCode 本地用量
   - DSH 本地用量
   - Claude Code 本地用量
   - Codex 本地用量

### 数据源

| 数据源 | 表 | account_id | key_id | channel/provider_id |
|-------|-----|-----------|--------|-------------------|
| OpenCode | usage_records | ✅ | ✅ | ❌ |
| CommandCode | usage_records | ✅ | ✅ | ❌ |
| ZCode | zcode_usage | ❌ | ❌ | ✅ (provider_id) |
| Claude Code | claudecode_usage | ❌ | ❌ | ✅ (channel) |
| DSH | dsh_* | ❌ | ❌ | ✅ (channel) |
| Codex | codex_* | ❌ | ❌ | ✅ (provider_id) |

### 核心问题

1. **信息扁平化**：所有数据源的汇总混在一起，无法区分各数据源的占比
2. **多账号混淆**：远程数据（OpenCode/CommandCode）可能有多个账号，但无法筛选
3. **本地数据割裂**：ZCode/DSH/Claude Code/Codex 各自独立展示，没有统一视图
4. **缺乏对比**：无法快速对比"OpenCode vs ZCode"的用量

## 方案 A：按数据源分层折叠（推荐）⭐

### 核心思路

按**数据源**（OpenCode、CommandCode、ZCode、Claude Code、DSH、Codex）分组，每个数据源一个折叠面板。

### 视觉设计

```
┌─────────────────────────────────────────────────────┐
│ 用量统计                                            │
│ [今天] [近7天] [近30天] [全部]                      │
├─────────────────────────────────────────────────────┤
│ 📊 全局汇总（所有数据源）                          │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐│
│ │总请求    │ │总 TOKEN  │ │总费用    │ │平均命中率││
│ │ 1,234    │ │ 456.7K   │ │ $12.34   │ │  42.3%   ││
│ └──────────┘ └──────────┘ └──────────┘ └──────────┘│
├─────────────────────────────────────────────────────┤
│ 🔽 OpenCode（BAI）              45.2% | $5.58       │ ← 可折叠
│  ├──────────────────────────────────────────────┤  │
│  │ 📊 234 请求 · 123.4K Token · 命中率 42%      │  │
│  │                                               │  │
│  │ 📧 账号 A (60%) | 📧 账号 B (40%)            │  │ ← 显示账号分布
│  │                                               │  │
│  │ 🔑 Top Keys:                                  │  │
│  │   • key-prod-001 (35%)                        │  │
│  │   • key-dev-002 (15%)                         │  │
│  │   • 其他 (50%)                                │  │
│  │                                               │  │
│  │ 📈 [模型用量图表]                            │  │
│  └──────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────┤
│ 🔽 ZCode（本地）                15.3% | $1.89       │
│  ├──────────────────────────────────────────────┤  │
│  │ 📊 67 请求 · 45.6K Token · 命中率 51%        │  │
│  │                                               │  │
│  │ 🔌 Top Providers:                             │  │ ← 显示 provider 分布
│  │   • GLM Coding Plan (80%)                     │  │
│  │   • GLM Start (20%)                           │  │

├─────────────────────────────────────────────────────┤

│ 🔽 DSH（本地）                   0%   | $0.00       │
```

### 特点

**优点**：
- ✅ 清晰的数据源层级，一眼看出各数据源占比
- ✅ 每个数据源内部可展示细分维度（账号/Key/Provider）
- ✅ 统一的折叠交互，信息密度可控
- ✅ 兼容所有数据源（远程 + 本地）

**缺点**：
- ❌ 需要重构现有的 page-stats 布局
- ❌ 全局图表（Token 构成、用量趋势）需要调整位置

**工时估算**：**25h**

## 方案 B：双栏布局（远程 vs 本地）

### 核心思路

将页面分为左右两栏：
- 左栏：远程数据（OpenCode/CommandCode）
- 右栏：本地数据（ZCode/Claude Code/DSH/Codex）

### 视觉设计

```
┌──────────────────────┬──────────────────────┐
│ 远程数据（云端）     │ 本地数据             │
├──────────────────────┼──────────────────────┤
│ 📊 OpenCode          │ 📊 ZCode             │
│   234 请求 | $5.58   │   67 请求 | $1.89    │
│   [账号 A] [账号 B]  │   [GLM Plan]         │
│                      │                      │
│ 📊 CommandCode       │ 📊 Claude Code       │
│   156 请求 | $3.96   │   45 请求 | $0.91    │
│   [账号 C]           │   [Anthropic]        │
│                      │                      │
│ [模型排行图表]       │ 📊 DSH               │
│                      │   0 请求 | $0.00     │
│ [用量趋势图表]       │                      │
│                      │ 📊 Codex             │
│                      │   0 请求 | $0.00     │
└──────────────────────┴──────────────────────┘
```

### 特点

**优点**：
- ✅ 远程/本地数据物理隔离，概念清晰
- ✅ 可独立滚动，互不干扰
- ✅ 适合宽屏显示

**缺点**：
- ❌ 移动端适配困难（需折叠为单栏）
- ❌ 横向对比不便（需要左右扫视）
- ❌ 屏幕宽度不足时拥挤

**工时估算**：**20h**

## 方案 C：Tab 分页（按数据源切换）

### 核心思路

顶部增加数据源 Tab，点击切换后，下方汇总数据和图表只显示该数据源的数据。

### 视觉设计

```
┌─────────────────────────────────────────────────────┐
│ 用量统计                                            │
│ [全部] [OpenCode] [CommandCode] [ZCode] [Claude]... │ ← Tab
├─────────────────────────────────────────────────────┤
│ 📊 当前数据源汇总                                   │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐            │
│ │总请求    │ │总 TOKEN  │ │总费用    │            │
│ └──────────┘ └──────────┘ └──────────┘            │
├─────────────────────────────────────────────────────┤
│ 📊 Token 构成（仅当前数据源）                      │
├─────────────────────────────────────────────────────┤
│ 📊 模型用量（仅当前数据源）                        │
├─────────────────────────────────────────────────────┤
│ 📊 用量趋势（仅当前数据源）                        │
└─────────────────────────────────────────────────────┘
```

### 特点

**优点**：
- ✅ 实现简单，复用现有图表逻辑
- ✅ 用户认知负担低（Tab 是常见交互）
- ✅ 每个数据源独立，信息清晰

**缺点**：
- ❌ 无法同时对比多个数据源
- ❌ "全部"Tab 下仍然混乱（除非默认不提供"全部"）
- ❌ 需要频繁切换 Tab 才能看到全貌

**工时估算**：**15h**

## 方案 D：仪表盘卡片网格（推荐，轻量级）⭐⭐

### 核心思路

将每个数据源做成独立的卡片，卡片内显示关键指标（请求数、Token、费用、占比），点击卡片可展开查看详细图表。

### 视觉设计

```
┌─────────────────────────────────────────────────────┐
│ 用量统计                                            │
│ [今天] [近7天] [近30天] [全部]                      │
├─────────────────────────────────────────────────────┤
│ 📊 全局汇总（所有数据源）                          │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐│
│ │总请求    │ │总 TOKEN  │ │总费用    │ │平均命中率││
│ └──────────┘ └──────────┘ └──────────┘ └──────────┘│
├─────────────────────────────────────────────────────┤
│ 数据源卡片（网格布局，2列或3列）                   │
├──────────────────────┬──────────────────────────────┤
│ ┌────────────────┐   │ ┌────────────────┐          │
│ │ OpenCode       │   │ │ CommandCode    │          │
│ │ 234 请求       │   │ │ 156 请求       │          │
│ │ 123.4K Token   │   │ │ 89.2K Token    │          │
│ │ $5.58 (45.2%)  │   │ │ $3.96 (32.1%)  │          │
│ │ [查看详情 →]   │   │ │ [查看详情 →]   │          │
│ └────────────────┘   │ └────────────────┘          │
├──────────────────────┼──────────────────────────────┤
│ ┌────────────────┐   │ ┌────────────────┐          │
│ │ ZCode          │   │ │ Claude Code    │          │
│ │ 67 请求        │   │ │ 45 请求        │          │
│ │ 45.6K Token    │   │ │ 32.1K Token    │          │
│ │ $1.89 (15.3%)  │   │ │ $0.91 (7.4%)   │          │
│ │ [查看详情 →]   │   │ │ [查看详情 →]   │          │
│ └────────────────┘   │ └────────────────┘          │
└──────────────────────┴──────────────────────────────┘

点击"查看详情"后，展开该数据源的详细图表（模型用量、趋势等）
```

### 特点

**优点**：
- ✅ 轻量级改造，不破坏现有布局
- ✅ 卡片网格直观，快速对比各数据源
- ✅ 点击卡片展开详情，按需加载
- ✅ 移动端友好（自动变单列）

**缺点**：
- ❌ 卡片内信息有限，需要点击才能看详情
- ❌ 展开详情后，页面会变长

**工时估算**：**12h**

## 方案 E：保持现状 + 增加筛选器

### 核心思路

保持现有布局不变，顶部增加"数据源筛选器"和"账号筛选器"，筛选后所有图表联动更新。

### 视觉设计

```
┌─────────────────────────────────────────────────────┐
│ 用量统计                                            │
│ [今天] [近7天] [近30天] [全部]                      │
│ 数据源: [全部▼] 账号: [全部▼]  ← 新增筛选器        │
├─────────────────────────────────────────────────────┤
│ 📊 汇总卡片（根据筛选条件动态更新）                │
├─────────────────────────────────────────────────────┤
│ 📊 Token 构成（根据筛选条件动态更新）              │
├─────────────────────────────────────────────────────┤
│ 📊 模型用量（根据筛选条件动态更新）                │
├─────────────────────────────────────────────────────┤
│ 📊 用量趋势（根据筛选条件动态更新）                │
├─────────────────────────────────────────────────────┤
│ ZCode 本地用量（根据筛选条件显示/隐藏）            │
│ DSH 本地用量（根据筛选条件显示/隐藏）              │
│ Claude Code 本地用量（根据筛选条件显示/隐藏）      │
│ Codex 本地用量（根据筛选条件显示/隐藏）            │
└─────────────────────────────────────────────────────┘
```

### 特点

**优点**：
- ✅ 改动最小，不改变现有布局
- ✅ 用户熟悉的筛选器交互
- ✅ 所有图表联动更新

**缺点**：
- ❌ 未解决"信息扁平化"问题（筛选后仍是混在一起）
- ❌ 无法同时对比多个数据源
- ❌ 数据源筛选器选项可能很多（6+ 个选项）

**工时估算**：**8h**

## 方案对比总结

| 方案 | 核心优势 | 核心劣势 | 工时 | 推荐度 |
|-----|---------|---------|------|--------|
| **A. 按数据源分层折叠** | 层级清晰，信息密度可控 | 需重构布局 | 25h | ⭐⭐⭐⭐ |
| **B. 双栏布局** | 远程/本地物理隔离 | 移动端适配难 | 20h | ⭐⭐ |
| **C. Tab 分页** | 实现简单 | 无法同时对比 | 15h | ⭐⭐⭐ |
| **D. 仪表盘卡片网格** | 轻量级，直观 | 卡片信息有限 | 12h | ⭐⭐⭐⭐⭐ |
| **E. 增加筛选器** | 改动最小 | 未解决核心问题 | 8h | ⭐ |

## 我的推荐

### 优先推荐：**方案 D（仪表盘卡片网格）** ⭐⭐⭐⭐⭐

**理由**：
1. **改动最小**：不破坏现有图表和本地数据区块
2. **直观对比**：卡片网格一眼看出各数据源占比
3. **按需展开**：点击卡片查看详情，不会信息过载
4. **工时最短**：12h（方案 A 需 25h）
5. **渐进式**：可先实现卡片网格，未来再升级为折叠面板

### 次选推荐：**方案 A（按数据源分层折叠）** ⭐⭐⭐⭐

**理由**：
1. **最彻底**：完全解决信息混乱问题
2. **可扩展**：未来可在每个数据源内再按账号/Key 细分
3. **用户体验最佳**：折叠交互成熟，信息层级清晰

**但工时较长（25h），建议分两期实施：P1 实现卡片网格（12h），P2 升级为折叠面板（+13h）**
