# 接入 chat.b.ai (BAI) 用量同步 — 实施文档

- 日期:2026-09-01
- 状态:方案已定案(全部决策确认 + 认证/接口实测通过),待开工
- 关联:GoGauge 增加 BAI 账号类型,与现有 opencode.ai 共存

## 1. 需求背景

现有 GoGauge 仅支持 opencode.ai 用量统计。用户询问是否能用 opencode 的取数方式获取 chat.b.ai/usage 用量。

**结论:架构不兼容,无法复用 opencode 的正则/server-fn 三件套,但 BAI 有标准 JSON/trpc 接口,可程序化接入(已验证 HTTP 200)。**

## 2. 抓包验证结论(已完成,2026-09-01)

通过浏览器自动化(headed Chrome + 手动登录)完成真实抓包与程序化复现验证。

### 2.1 平台识别

- chat.b.ai = **LobeChat fork**(BAI 定制版),Next.js + tRPC + Auth.js(NextAuth)
- 用量页 `/usage` 数据**不在 HTML 中**,全部客户端拉取 → opencode 的"抓 HTML 正则解析"思路失效

### 2.2 认证机制(已实测:仅需 Cookie,XOR 头非必需)

| 因子 | 形式 | 必要性 |
|---|---|---|
| Cookie | `__Secure-authjs.session-token` + `__Host-authjs.csrf-token` + `__Secure-authjs.callback-url`(3 个,HttpOnly,域均为 chat.b.ai) | **必需**(主认证) |
| 请求头 | `X-ainft-chat-auth` | **非必需**(浏览器会带,但后端不校验它) |

**实测结论(2026-09-01 复核):** 仅带 Cookie、不带 `X-ainft-chat-auth`,`usage.points / usage.summary / usage.records / user.getUserState` **全部 HTTP 200**。先前误判 XOR 头必需,是因为对照实验缺 Cookie(credentials:'omit')而非缺 XOR 头。**BAI 接口认证 = Cookie 单因子**。

XOR 头算法(供参考,实现可不带):
```python
import base64, json
key = "LobeHub · LobeHub".encode("utf-8")          # \xb7 是 U+00B7,注意 UTF-8 编码
payload = {"accessCode": "", "userId": "user_XXX",
           "runtimeProvider": "openai"}             # 纯静态
auth = base64.b64encode(
    bytes(c ^ key[i % len(key)]
          for i, c in enumerate(json.dumps(payload, separators=(",", ":")).encode()))
).decode()
```
载荷与 key 均不随时间变化。实现侧**不必生成**此头,仅当未来 BAI 收紧校验时再启用。

### 2.4 其他已确认

- `user.getUserState` 返回 `userId`、`apiAccessToken`(JWT)等,但**认证不需要 userId 也不需要 apiAccessToken**(见 §2.2)。userId 仅作记录归属/调试参考,本期可不存。
- 全程仅需 3 个请求(usage.points / summary / records)即可对齐用量页数据,无需批次页并发

## 3. 技术方案

### 3.1 新增文件 `app/bai_api.py`(新模块,不扩展 opencode_api.py)

理由:认证模型(cookie jar vs auth cookie)、接口形态(JSON trpc vs HTML/server-fn 正则)均不同,独立文件保持单一职责。与 `app/opencode_api.py` 平级。

内容:
1. `fetch_usage_points(cookies)` → `{points_balance, points_expiring}`
2. `fetch_usage_summary(cookies)` → `{monthly_chart, monthly_spent}`
3. `fetch_usage_records(cookies, cursor, page_size=...)` → `{data, has_more, next_cursor, page, pageSize}`(注意响应键是 `data` 非 `items`,见 §2.3)
4. `parse_usage_record(item) -> dict` — BAI JSON → 数据库字典映射
5. HTTP 工具复用/复制 `_fetch`(重试/超时),认证仅需 Cookie 头(见 §2.2,无 XOR 头)

### 3.2 数据层 `app/db.py` 变更

**`accounts` 加 1 列**(幂等迁移):
```sql
ALTER TABLE accounts ADD COLUMN source TEXT NOT NULL DEFAULT 'opencode'  -- 'opencode' | 'bai'
```
(无需 user_id 列 —— 认证仅需 cookie,§2.2/D4)

**`add_account` 去重适配**(G5):现按 `TRIM(token)` 判同;BAI 每次登录 cookie 不同,需按 source 分支 —— `source='bai'` 时不按 token 去重(或按用户标识),避免重登同账号产生重复行。其余凭证函数(get_token/get_account_credentials)**零改动**,BAI 的 token 即 cookie jar JSON 字符串,同列存读。

**`usage_records` 不扩列**:BAI 成本(走本地定价表)写入现有 `cost_raw/cost_usd`,便于与 opencode 统一聚合。

**`usage_records.usg_id` 主键兼容**:BAI id 为 `api_` 前缀,与 opencode `usg_` 天然不冲突,无需改主键。

**字段映射**(BAI JSON → usage_records):
| usage_records | BAI | 说明 |
|---|---|---|
| usg_id | id | 前缀 `api_`,天然区分 |
| created_at | created_at | 同名 |
| model | model | 同名 |
| provider | — | 置 `'bai'` 或留空 |
| input_tokens | input_tokens | 同名 |
| output_tokens | output_tokens | 同名 |
| reasoning_tokens | 无 | 0 |
| cache_read_tokens | cache_tokens.cache_read_input_tokens | 同名 |
| cache_write_5m_tokens | cache_tokens.cache_creation_5m_tokens | 语义近似 |
| cache_write_1h_tokens | cache_tokens.cache_creation_1h_tokens | 语义近似 |
| (忽略) | cache_tokens.cache_creation_input_tokens | **G4:实测全 0 且语义不明,本期不映射记 0;若未来非 0 需确认归属** |
| cost_raw / cost_usd | **本地定价表 × token → 美元** | 见 §4-D1,不扩列 |
| key_id / session_id / plan | 无 | NULL |

`insert_usage_records` 已按 `usg_id` upsert,BAI 记录可复用,无需改写入逻辑。

### 3.3 同步调度 `app/server.py` 变更

现有 `_sync_one_account` 假设 opencode 协议(resolve_workspace_id → fetch_usage_page)。改造:
- 按 `accounts.source` 分发:`sync_usage` 遍历账号时,`source='bai'` 走 `bai_api` 同步分支;`source='opencode'`(默认)走原逻辑
- **BAI 分页/增量策略(G3,已定案)**:不存 cursor。每轮从第 1 页(pageSize 拉大,如 100)翻页,每页入库前先按 `usg_id` 查库:该页任一记录已存在 → 该页及后续全为旧数据 → 停止(upsert 去重天然支持增量)。全量模式翻到 `has_more=false`。`deepest_page_fetched` 等 opencode 专用列对 BAI 不使用
- BAI 分支新数据入库走 `insert_usage_records`(usg_id upsert 复用),`usage_sync_state` 复用(account_id 主键已支持多账号)
- 配额缓存:`fetch_quota` 是 opencode 专属(dashboard HTML),BAI 账号配额由 `usage.points` 提供 → 需在 `_fetch_quota_with_cache` 按 source 分流

**BAI 配额数据结构(用户已确认:映射成一格"余额 X 积分"):**
- opencode:`quota.windows[]`(5h/weekly/monthly 百分比窗口,前端 `renderUsageBlocks` 渲染)
- BAI:`usage.points` 返回 `{points_balance, points_expiring}`,映射为单格:
  ```json
  { "windows": [{ "label": "Points", "used": 0, "remaining": 100,
                  "total": 100, "unit": "points", "points_balance": 300000,
                  "points_expiring": 300000, "reset_in_sec": null }] }
  ```
- 前端 `renderUsageBlocks` 需兼容:遇 `unit == "points"` 或 `points_balance` 存在时,渲染单格显示"余额 300,000 积分"(不走百分比进度条,展示余额数字 + 赠送/到期提示)
- 配额卡标注"估算/预算口径"提示沿用 §4-D2 前端标记

### 3.4 登录流 `app/auth.py` 变更

- opencode:加载 `auth.opencode.ai/authorize` → 抓 `auth` cookie
- BAI:加载 `https://chat.b.ai/login` → 登录成功后抓 3 个 `__Secure-authjs.*` / `__Host-authjs.*` cookie(主认证,§2.2)
- 落库:`accounts.token` 存 cookie jar 序列化(JSON)+ source='bai'
- 单个 LoginWatcher 需支持登录 URL 与 cookie 名可配置(新增参数),或分支处理

**BAI 登录成功判定(G2,已定案):**
```
判定条件(与 opencode 同模式,判据不同):
  opencode: URL 在 https://opencode.ai 域 + auth cookie 存在
  BAI:      URL 在 https://chat.b.ai 域 + __Secure-authjs.session-token 非空
```
- 轮询窗口 URL:仍在 Google OAuth / 登录中间页 → 未成功;回落 chat.b.ai 域 → `get_cookies()` 读 HttpOnly cookie 验证 session-token
- 仅 csrf/callback-url 两个 cookie 不算成功(登录前即存在)——**必须 session-token 非空**
- 抽纯函数 `_extract_bai_session(cookies) -> str|None` 供单测(mock cookie 三态:有 session-token / 仅 csrf / session-token 空值)

**token 存取适配(G5,已定案):**
- `db.py` 凭证读取函数(`get_account_credentials`/`get_token`)**零改动**,返回值不变 —— BAI 的 token 就是 cookie jar JSON 字符串,同列存储同列读取;唯一 db.py 改动是 `add_account` 去重分支(见 §3.2)
- `bai_api.py` 内加 `build_cookie_header(cookie_jar_json) -> str`:反序列化 JSON,拼 `name=value; name2=value2` Cookie 头
- **账号去重**:`add_account` 现按 `TRIM(token)` 判同 —— BAI 每次登录 cookie 不同,重登同账号会产生重复行。BAI 账号去重按 `source='bai'` + `workspace_id`(存 BAI 返回的用户标识)判定;实现时在 `add_account`/登录落库路径按 source 分支

### D4:BAI 认证 — 仅需 Cookie,无需 userId/XOR(验证结论,已简化)

**【已实测】`X-ainft-chat-auth` XOR 头非必需;认证 = 3 个 Auth.js cookie 即可。** 无 userId 获取链路,无临时 XOR 占位问题。原 D4 设计(登录→占位 XOR→getUserState 取 userId→重算头)整个取消。

- 登录成功后仅存 cookie jar,立即可用于全部 3 个 usage 端点
- 若未来 BAI 收紧校验(XOR 头变为必需),再补 §2.2 的 XOR 算法与 userId 获取(此时 userId 可从 `user.getUserState` 拿,仅需 cookie)

## 4. 关键决策分歧点(需用户确认)

### D1:成本口径 — 单一成本,本地模型定价表计算(用户已确认)

**【已确认】单一成本,统一美元,**不用** BAI 官方接口定价、不用 `cost_points` 积分。每条约账记录用**本地模型定价表**按 token 消耗算美元,写入现有 `cost_raw/cost_usd`(与 opencode 同一对列,口径统一可比)。

机制:
1. **定价表**:`C:\Users\11013\.cc-switch\model-pricing.json`
   - 结构:`models[]` 每项为 `modelId` + `inputCostPerMillion/outputCostPerMillion/cacheReadCostPerMillion/cacheCreationCostPerMillion`(字符串,单位 每百万 token USD)
   - 匹配:按 `modelId`,并剥 BAI 模型名的 provider 前缀(如 `glm/glm-5.3-flash` → `glm-5.3-flash`)再匹配
   - 未收录模型 / 文件缺失 / 读取失败 → 该记录成本记 0,不影响主流程
2. **成本计算**:每条记录 `cost = input×in + output×out + cache_read×cr + cache_write×(c5m+c1h)×cw`,换算为 1e-8 USD 存 `cost_raw`,`cost_usd = cost_raw/1e8`。沿用 CLAUDE.md「口径约定」。
3. **不扩列**:复用现有 `cost_raw/cost_usd`,opencode 记录不受影响(各自算各自 modelId 的成本)。

注:这会让 BAI 账号成本与 BAI 官方实际扣费(积分)不完全一致,属"预算/参考口径",仅内部参考。此为预期行为。

### D2:账号 source 标记 — accounts 加 source 列 + 前端展示【已确认做前端】

- 后端:`accounts.source` 单列,`sync_usage` 按其分流(opencode / bai 两套拉数逻辑)。**必做**,无此则无法区分账号类型。
- 前端**【已确认做】**:
  1. **账号来源徽标**:多账号列表(设置页 + 用户菜单)每账号显示 opencode / BAI 来源标记,多账号混合时一眼区分归属平台
  2. **配额卡"估算"标注**:BAI 配额来自 `usage.points`(积分),成本卡标注此为"估算/预算口径"(因 BAI cost_usd 来自本地定价表,非实际扣费)
  3. **成本口径提示**:BAI 账号成本与 opencode 实际美元含义不同,统计页/趋势图对 BAI 数据标注来源口径

  后端按 `account_id` 关联账号 source,`/api/dashboard`、`/api/accounts` 等响应带出 `source` 字段供前端渲染。

### D3:登录交互

- **A(推荐):沿用现有 WebView 登录窗框架,LoginWatcher 参数化登录 URL/cookie 名,新增"添加 BAI 账号"入口**【已确认选 A】
  - 登录窗加载 BAI 登录页(`chat.b.ai/login`),登录成功后抓 3 个 authjs cookie
  - BAI 与 opencode 共用一个登录窗组件,按账号类型参数化

## 7. 风险与备注

- `usage.records` 分页参数、`next_cursor` 结构以实测为准,上线前再抓一次全量翻页确认
- 接口可能变更:LobeChat fork 升级会改 trpc 路径,需留错误处理
- cookie 会过期(Auth.js 会话),过期需重新登录,与 opencode token 过期体验一致
- **安全**:cookie jar 含真实会话凭证,落库后等同现有 token 存储,仅存本地 SQLite
- 本实施文档不签入(按项目约定 doc/ 下文档不入库)
